01The architect's view: where Keyspaces fits

Read this section first. It gives the decision. The sections after it teach how the Cassandra model works.

In short: Amazon Keyspaces is a serverless, managed database that is compatible with Apache Cassandra. It stores very large amounts of rows, grouped by a partition key and sorted inside each partition. It answers "the rows of this one key, in this order" fast at any size. Choose it when you write a lot, read by a known key, and want the Cassandra language and drivers without the Cassandra servers.

The data model is a {{ k.term("wide-column store", "wide-column-store") }}. Each partition is like one long, sorted list of rows that belong together. An example is all events of one user.

The questions that an architect asks, in this order

  1. Which value does each read know? That value is the partition key.
  2. In which order do the reads want the rows? That order is the clustering order.
  3. How large does one partition get? Endless partitions are a problem. Split them, for example by user and month.
  4. How many different queries? One table for each query. Each event can be written to two or three tables.
  5. How long must the data stay? That is the TTL.
  6. Does the team use Cassandra now? If yes, Keyspaces keeps the code. If no, compare it with DynamoDB.
  7. Who needs reports? Plan an export to an analytics engine. Do not run reports on Keyspaces.

Apache Cassandra and CQL: the model

Partitions, clustering columns, and one table for each query.

02Why a wide-column store? The filing cabinet

An office keeps one drawer for each customer. In each drawer, the papers are always in date order, newest at the front. A new paper goes into its place at once.

{% call k.callout("analogy", "Analogy") %}

"The last 10 papers of customer 5" is easy: open one drawer, take 10 from the front. "All papers of type invoice, of all customers" is hard: you must open every drawer. The drawer label is the partition key. The date order inside the drawer is the clustering order.

{% endcall %}

Apache Cassandra was built for very high write rates spread over many machines. It gives up JOIN, GROUP BY and indexes on any column. In return, a read with the partition key goes to one partition, and the work does not grow with the size of the table.

03The model: partitions of sorted rows

A CQL table looks like a SQL table. It has columns and rows. The difference is in the {{ k.term("primary key") }}, which has two parts with two different jobs:

  • The {{ k.term("partition key") }} selects the partition. Keyspaces keeps all rows with the same partition key value together.
  • The {{ k.term("clustering column") }}s sort the rows inside a partition. The sort happens at write time, so a read gets the rows already in order.

This is the real table of Lale Market:

{% call k.sql("T1", "The activity table") %} 
CREATE TABLE dbws.activity_by_user (
  user_id    text,
  event_time timestamp,
  event_id   uuid,
  event_type text,
  product_id text,
  detail     text,
  PRIMARY KEY ((user_id), event_time, event_id)
) WITH CLUSTERING ORDER BY (event_time DESC)
  AND default_time_to_live = 604800;
dbws.activity_by_userThe table activity_by_user in the keyspace dbws. A keyspace is a group of tables, like a database.
user_id textThe id of the user (the visitor id or a customer id).
event_time timestamp, event_id uuidWhen the event happened, and a unique id for it.
PRIMARY KEY ((user_id), event_time, event_id)The inner parentheses hold the partition key: user_id. The other two are clustering columns. Together they identify one row. event_id keeps two events of the same millisecond apart.
CLUSTERING ORDER BY (event_time DESC)Inside each partition, keep the rows newest first.
default_time_to_live = 604800Each row expires 604,800 seconds (7 days) after its write.

A condition on the first clustering column is a range inside one partition: WHERE user_id = 'C00005' AND event_time > '2026-10-26'. The rows are in time order, so Keyspaces reads one continuous slice.

The simulation uses a small teaching token (the customer number modulo 3). Keyspaces uses its own partitioner. The default is the Cassandra-compatible Murmur3Partitioner (Functional differences).

05The question without a partition key

"The last purchases of all users" gives no partition key. To answer it, the database must look in each partition.

{{ k.sim("nokey", "A filter on event_type with no partition key") }}

Apache Cassandra refuses such a query unless you add ALLOW FILTERING, because its cost grows with the table. Keyspaces does not support CREATE INDEX, and it has no aggregate functions such as count() (Supported Cassandra APIs). So the rule is: design one table for each query. If the shop needs "purchases by product", it writes each purchase a second time into a table with PRIMARY KEY ((product_id), event_time, event_id). Two writes for one event is normal here. Storage is cheaper than a read of all partitions on each request.

{{ k.quiz("ks-q1", "Which query can Keyspaces answer from one partition of activity_by_user?", ["All events of type purchase from all users", "The 10 users with the most events", "The events of C00005 after 10:00 today", "All events of product P0130"], 2, "Only this query gives the partition key (user_id). The time condition is on the first clustering column, so it is a slice of one partition.") }}

06Consistency levels and their cost

Keyspaces "replicates all write operations three times across multiple Availability Zones". Writes use LOCAL_QUORUM: two of the three replicas must have the write before Keyspaces reports success (Consistency levels). For reads, you select the level:

Read levelWhat it doesCost per 4 KB (on-demand)
LOCAL_QUORUMReturns the result of all writes that succeeded before the read.1 RRU
LOCAL_ONE / ONEFaster and more available, but it "might not reflect the results of a recently completed write".0.5 RRU

07TTL: old events go away

The table has default_time_to_live = 604800 (7 days). Each row expires 7 days after its write. The Load Simulation writes with USING TTL 600, so its synthetic rows expire after 10 minutes.

{% call k.callout("warn", "Note for the workshop") %}

The TTL counts from the write time, not from event_time. The Seed writes 30 days of history at once, and all seeded rows expire 7 days after the Seed. If the activity page shows no rows for a persona, ask your instructor to run the Seed again.

08Running Cassandra yourself, and what Keyspaces changes

Apache Cassandra runs on a ring of nodes. A hash of the partition key (the token) decides which nodes hold the partition. A client sends a request to any node, and that node becomes the {{ k.term("coordinator") }}. The coordinator sends the request to the nodes that hold the partition, and it returns the answer.

{{ k.fig("keyspaces-cassandra-cluster.png", "a client sends CQL to one node of a ring of four nodes. In Apache Cassandra, you install, size and operate these nodes yourself.") }} {{ k.fig("keyspaces-coordinator.jpg", "the coordinator (orange) receives the request from the client and sends it to the other nodes of the ring (dashed arrows). The client talks to one node only.") }}

When you run Cassandra yourself, you size the nodes, and you add nodes and move data when it grows. You run the process that makes the copies equal again (nodetool repair) and tune compaction. You also take backups and update every node. Keyspaces is serverless: there are "no clusters, hosts, or Java virtual machines (JVMs) to configure" (Functional differences).

{{ k.fig("keyspaces-serverless.png", "Cassandra drivers, cqlsh and the console send CQL requests over TLS to Amazon Keyspaces. Keyspaces writes to encrypted storage. You see no nodes.") }}
