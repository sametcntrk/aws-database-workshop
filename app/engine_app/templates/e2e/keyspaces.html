00What you will learn

Each Lale Market page writes an activity event: a view, a search, an "add to cart". The shop needs "the newest events of one user" in milliseconds, for "Recently viewed" and "My activity". The number of events grows each day, and it never stops. Amazon Keyspaces (for Apache Cassandra) stores these events. It is a {{ k.term("wide-column store") }} that speaks the Cassandra Query Language (CQL).

After this tutorial, you can do these tasks:

  1. Explain the two parts of a Cassandra primary key: the partition key and the clustering columns.
  2. Design a table for one query, and say why "one table per query" is normal here.
  3. Predict which CQL queries Keyspaces can answer, and which it cannot.
  4. Select a read consistency level, and know its cost.
  5. Use a table TTL for data that loses its value with time.

01The model: partitions of sorted rows

A CQL table looks like a SQL table: it has columns and rows. The difference is in the {{ k.term("primary key") }}. It has two parts with two different jobs:

  • The {{ k.term("partition key") }} selects the partition. Keyspaces keeps all rows with the same partition key value together.
  • The {{ k.term("clustering column") }}s sort the rows inside a partition. The sort happens at write time, so a read gets the rows already in order.

This is the real table of Lale Market (from META.model of the Engine App):

CREATE TABLE dbws.activity_by_user (
  user_id    text,                 -- partition key: one partition per user
  event_time timestamp,            -- clustering column 1: sort by time
  event_id   uuid,                 -- clustering column 2: two events in the same millisecond stay unique
  event_type text, product_id text, detail text,
  PRIMARY KEY ((user_id), event_time, event_id)
) WITH CLUSTERING ORDER BY (event_time DESC)     -- newest first
  AND default_time_to_live = 604800;            -- 7 days

Read PRIMARY KEY ((user_id), event_time, event_id) from left to right. The inner parentheses hold the partition key. The rest are clustering columns. This is a real slice of the partition of Zeynep Şahin (C00005), who browses a lot:

02Reads that Keyspaces answers well

{% call k.predict("You ask for the 10 newest events of C00005. The table has events of 1,000 users. How many partitions does Keyspaces read, and does it sort anything?") %}

One partition, and no sort at read time. The partition key goes straight to the partition of C00005. The rows are already newest first, so Keyspaces reads the first 10 rows and stops.

{% endcall %} {% call k.query("keyspaces", "K1", "The 10 newest events of one user") %} 
SELECT user_id, event_time, event_type, product_id, detail
FROM dbws.activity_by_user WHERE user_id = 'C00005' LIMIT 10;

This is the query behind "Recently viewed" on the product page (with your browser id as user_id).

{% endcall %} {% call k.query("keyspaces", "K2", "A time range inside one partition") %} 
SELECT event_time, event_type, product_id
FROM dbws.activity_by_user WHERE user_id = 'C00005' AND event_time > <now - 24 hours>;

A condition on the first clustering column is a range read. The rows are in time order, so Keyspaces reads one continuous slice.

{% endcall %} {% call k.query("keyspaces", "K3", "How many rows does one partition hold?") %} 
SELECT event_time FROM dbws.activity_by_user WHERE user_id = 'C00005';   -- the Engine App counts the rows

Keyspaces does not support aggregate functions such as count() (Supported Cassandra APIs). An app that needs counts keeps a counter, or it counts in a different Engine.

{% endcall %}

03The question without a partition key

"Show the last 5 purchases of all users" gives no partition key. To answer it, the Engine must look in each partition. Apache Cassandra refuses such a query unless you add ALLOW FILTERING, because its cost grows with the size of the table.

{% call k.query("keyspaces", "K4", "A filter on a regular column, with no partition key") %} 
SELECT user_id, event_type FROM dbws.activity_by_user WHERE event_type = 'purchase' LIMIT 5;

Run it and read the answer of Keyspaces. Then compare it with K1: the same table, but a different kind of question.

{% endcall %}

Keyspaces also does not support CREATE INDEX. So the rule is: design one table for each query. If the shop needs "events by product", it writes each event a second time into a table with PRIMARY KEY ((product_id), event_time, event_id). Two writes for one event is normal in this model. Storage is cheaper than a full-table read on each request.

{{ k.quiz("ks-q1", "Which query can Keyspaces answer from one partition of activity_by_user?", ["All events of type purchase from all users", "The events of user C00005 after 10:00 today", "The 10 users with the most events", "All events of product P0130"], 1, "Only this query gives the partition key (user_id). The time condition is on the first clustering column, so it is a slice of one partition.") }}

04Where the partitions live

Apache Cassandra runs on a ring of nodes. A hash of the partition key (the token) decides which nodes hold the partition. A client sends a request to any node. That node becomes the {{ k.term("coordinator") }}: it sends the request to the nodes that hold the partition and returns the answer.

{{ k.fig("keyspaces-cassandra-cluster.png", "a client sends CQL to one node of a ring of four nodes. In Apache Cassandra, you install, size and operate these nodes yourself.") }} {{ k.fig("keyspaces-coordinator.jpg", "the coordinator (orange) receives the request from the client and sends it to the other nodes of the ring (dashed arrows). The client talks to one node only.") }}

Amazon Keyspaces gives you the CQL interface without the nodes. It is serverless: there are "no clusters, hosts, or Java virtual machines (JVMs) to configure" (Functional differences). Lale Market connects with the open-source Python Cassandra driver, through a VPC interface endpoint, with IAM (SigV4) authentication instead of a password.

{{ k.fig("keyspaces-serverless.png", "Cassandra drivers, cqlsh and the console send CQL requests over TLS to Amazon Keyspaces. Keyspaces writes to encrypted storage. You see no nodes.") }}

05Consistency levels and their cost

Keyspaces "replicates all write operations three times across multiple Availability Zones". Writes always use LOCAL_QUORUM (Consistency levels). For a read, you select the level:

Read levelWhat it doesCost per 4 KB (on-demand)
LOCAL_QUORUMReturns the result of all writes that succeeded before the read.1 RRU
LOCAL_ONE / ONEFaster and more available, but it "might not reflect the results of a recently completed write".0.5 RRU
{% call k.query("keyspaces", "K5", "The same read as K1 with LOCAL_ONE") %} 
CONSISTENCY LOCAL_ONE;
SELECT user_id, event_time, event_type, product_id FROM dbws.activity_by_user WHERE user_id = 'C00005' LIMIT 10;

The result is the same here, because nobody wrote to this partition in the last moment. The bill is half.

{% endcall %} {{ k.quiz("ks-q2", "\"Recently viewed\" can be one second old. Which read level is the better choice for it?", ["LOCAL_ONE, because it costs half", "LOCAL_QUORUM, because it is newer", "EACH_QUORUM, for all the regions", "ALL, to read every copy of the data"], 0, "A short delay is acceptable for this strip, so the cheaper level is enough. EACH_QUORUM and ALL are not supported by Keyspaces.") }}

06TTL: old events go away

The table has default_time_to_live = 604800 (7 days). Each row expires 7 days after its write, and Keyspaces deletes it. The Load Simulation writes with USING TTL 600, so its synthetic rows expire after 10 minutes.

{% call k.callout("warn", "Note for the workshop") %}

The TTL counts from the write time, not from event_time. The Seed writes 30 days of history in one go. All seeded rows expire 7 days after the Seed. If K1 returns no rows, ask your instructor to run the Seed again.

{% endcall %} {% call k.query("keyspaces", "K7", "Read the table settings") %} 
SELECT default_time_to_live, custom_properties FROM system_schema_mcs.tables
WHERE keyspace_name = 'dbws' AND table_name = 'activity_by_user';

system_schema_mcs is a Keyspaces system keyspace. It shows settings that Apache Cassandra does not have, such as the capacity mode.

{% endcall %}

07When to use it, and when not

Good fitWhy
Activity feeds, clickstreams, event history per user or deviceMany writes, and reads of "the newest N for one key".
Apps that already use Apache CassandraThe same CQL and drivers, with no nodes to operate.
Messages per conversation, orders per customer (as a read model)One partition per owner, sorted by time.
Weak fitBetter choice
Ad hoc questions across all partitionsRedshift or Aurora
Metrics that you aggregate by time windowsTimestream for InfluxDB
Joins and multi-row transactions with rulesAurora
