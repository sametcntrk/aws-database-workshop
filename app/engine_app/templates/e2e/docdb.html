00What you will learn

Lale Market keeps its product catalog in Amazon DocumentDB. A product page needs the product with all its details in one read. Products of different types have different attributes. A document database stores each product as one JSON document, with nested fields and arrays.

After this tutorial, you can do these tasks:

  1. Read a real product document and name its nested objects and arrays.
  2. Write a filter on a nested field and on an array, with a projection.
  3. Read an explain plan and tell an index scan (IXSCAN) from a collection scan (COLLSCAN).
  4. Build an aggregation pipeline that unwinds an array and groups the result.
  5. Decide between "embed in one document" and "reference another collection" for a piece of data.

01The model: one document for one thing

A {{ k.term("document") }} is a set of field and value pairs, like a JSON object. A value can be a number, a text, an array or a second document (a nested object). Documents of one kind go into a {{ k.term("collection") }}. A collection has no schema: two documents in one collection can have different fields.

{% call k.predict("A relational shop needs a products table, an attributes table and a tags table for this data. How many reads does DocumentDB need to return one product with its attributes and tags?") %}

One read. The attributes are a nested object and the tags are an array inside the same document. Run M1 and look at the result.

{% endcall %} {% call k.query("docdb", "M1", "Read one product document by _id") %} 
db.products.find_one({ _id: 'P0001' })

Purpose: see the full document as DocumentDB stores it. _id is the primary key of each document. DocumentDB always indexes it.

This is the result (the live result above is the same document):

{
  "_id": "P0001",
  "name": "Alpen Kablosuz Kulaklık 1",
  "category": "Elektronik",  "brand": "Alpen",  "type": "Kablosuz Kulaklık",
  "price": 3373.84,  "stock": 128,  "color": "siyah",  "rating": 4.8,

Compare this with the relational model of the Aurora tutorial. There, the product has a set shape, and a list of tags needs its own table. Here, the shape of the data in storage is the shape that the product page shows.

{% call k.callout("analogy", "Analogy") %}

A relational database is like a set of ledgers. One ledger for products, one for attributes, one for tags. To see a product, you open three ledgers and match the numbers. A document database is like a folder for each product. Everything about the product is in its folder. You open one folder.

{% endcall %}

A document can be up to 16 MiB and nest up to 200 levels (DocumentDB quotas). A product document of Lale Market is about 500 bytes. The limit is far away, but it is real: a list that grows without an end does not belong in one document.

Purpose: see the number of documents, the average document size and the number of indexes.

{% endcall %}

02Find: filters, nested fields, arrays, projections

A find has two parts. The filter selects documents. The {{ k.term("projection") }} selects the fields that come back. Dot notation reaches into a nested document: 'attributes.renk' is the field renk inside attributes.

{% call k.query("docdb", "M2", "Black electronics, cheapest first, only four fields") %} 
db.products.find(
  { category: 'Elektronik', 'attributes.renk': 'siyah' },                   // filter
  { name: 1, price: 1, 'attributes.renk': 1, 'attributes.garanti_ay': 1 }   // projection
).sort({ price: 1 })

Both conditions must be true (an implicit AND). The projection makes the result smaller, so less data goes over the network. The Engine still reads the full document from storage.

{% endcall %}

A filter on an array field has a special meaning. { tags: 'indirim' } does not mean "tags equals the text 'indirim'". It means "one element of the array tags is 'indirim'".

{% call k.query("docdb", "M3", "Products with the tag indirim") %} 
db.products.find({ tags: 'indirim' }, { name: 1, tags: 1 }).limit(10)
{% endcall %} {% call k.query("docdb", "M8", "A range on a nested field and a range on a top-level field") %} 
db.products.find(
  { 'attributes.garanti_ay': { $gte: 36 }, rating: { $gte: 4.5 } },
  { name: 1, rating: 1, 'attributes.garanti_ay': 1 }
).sort({ rating: -1 })

$gte means "greater than or equal". Operators start with $, so the Engine can tell them from field names.

{% endcall %} {{ k.quiz("docdb-q1", "A document has tags: ['yeni', 'indirim']. Which filter matches it?", ["{ tags: 'indirim' }", "{ tags: 'indirim, yeni' }", "{ 'tags.indirim': true }", "{ tags: { $size: 1 } }"], 0, "A filter on an array field with one value matches when one element equals the value. The array has two elements, so $size: 1 does not match.") }}

03Indexes: what DocumentDB reads to answer

Without an index, DocumentDB must test each document of the collection. This is a {{ k.term("collection scan") }} (COLLSCAN). An index keeps the values of one or more fields in a sorted tree, and each entry points to a document. DocumentDB can then go straight to the matching documents (IXSCAN).

{{ k.fig("docdb-btree.png", "each node keeps its keys in sorted order. A search goes from the root to one leaf and reads one node on each level. An index on { category, rating } sorts first by category, then by rating inside each category.") }} {% call k.query("docdb", "M6", "The indexes of the products collection") %} 
db.products.getIndexes()

Expected: _id_, category_1_rating_-1 (a compound index), attributes.renk_1 (an index on a nested field) and rating_-1. 1 means ascending order and -1 means descending order.

{% endcall %} {% call k.predict("The catalog has 200 products, 40 in each category. You ask for the books (category Kitap), sorted by rating. How many documents does DocumentDB examine with the index, and how many without it?") %}

With the index on { category, rating }: 40. The index goes to the start of "Kitap" and reads its 40 entries, already sorted by rating. Without the index: 200. DocumentDB reads each document, keeps 40, and then it must sort them in memory (a SORT stage). Run M4 to check.

{% endcall %} {% call k.query("docdb", "M4", "Explain the same query with and without the index") %} 
db.products.find({ category: 'Kitap' }).sort({ rating: -1 }).limit(48).explain('executionStats')
db.products.find({ category: 'Kitap' }).sort({ rating: -1 }).limit(48).hint({ $natural: 1 }).explain('executionStats')

hint({ $natural: 1 }) tells DocumentDB to read the documents in storage order, so it forces a collection scan. Compare "docs examined" and the stages: IXSCAN in the first plan, COLLSCAN and SORT in the second.

{% endcall %}

The order of fields in a compound index matters. { category: 1, rating: -1 } helps "books, best first". It does not help "all products with rating above 4.5", because the tree sorts by category first. For that question, Lale Market has the separate index { rating: -1 }.

{{ k.quiz("docdb-q2", "A query filters on brand only. The collection has the index { category: 1, rating: -1 } and no other index on brand. What does DocumentDB do?", ["It uses the compound index for the brand", "It examines each document of the collection", "It creates an index on brand by itself", "It returns an error for a missing index"], 1, "No index starts with brand, so no index can find the matching documents. The result is a COLLSCAN.") }}

04Aggregation: a pipeline of stages

An {{ k.term("aggregation pipeline") }} is a list of stages. Each stage takes documents, changes them, and gives them to the next stage. The Lale Market home page uses $group to count the products of each category on the server.

{% call k.query("docdb", "M5", "How many products have each tag, and their average price") %} 
db.products.aggregate([
  { $unwind: '$tags' },                                                    // 1 document with 2 tags → 2 documents
  { $group: { _id: '$tags', products: { $sum: 1 }, avg_price: { $avg: '$price' } } },
  { $sort: { products: -1 } }
])
  1. $unwind makes one document for each element of tags. P0001 with ["hızlı kargo", "çevreci"] becomes two documents, one with each tag.
  2. $group puts the documents with the same tag together. It counts them and averages the price.
  3. $sort puts the most common tag first.
{% endcall %} {{ k.quiz("docdb-q3", "Each of the 200 products has exactly 2 tags. How many documents leave the $unwind stage?", ["200 documents", "400 documents", "2 documents", "6 documents"], 1, "$unwind makes one output document for each array element: 200 × 2 = 400.") }}

05Design: embed or reference?

The main design question in a document database is where each piece of data lives. Two options:

  • Embed: put the data inside the parent document (the attributes and tags of a product). One read returns all of it.
  • Reference: keep the data in its own collection, and store its _id in the parent (like a foreign key, but DocumentDB does not check it).
DataLale Market choiceWhy
Attributes and tags of a productEmbedSmall, always read with the product, belongs to one product only.
Orders of a customerNot in DocumentDB (Aurora)The list grows without an end, and an order needs a transaction with the stock.
Reviews of a product (if the shop adds them)Reference, or embed the newest 5Thousands of reviews make one document too large. The page shows only a few.
{% call k.callout("warn", "Common mistake") %}

Do not embed a list that grows with time, such as all orders or all page views. The document gets larger with each write, and a read returns data that the page does not need. Lale Market keeps page views in Keyspaces, one row per event.

{% endcall %}

06The DocumentDB cluster

Amazon DocumentDB (with MongoDB compatibility) speaks the MongoDB API. The Lale Market Engine App uses the standard Python MongoDB driver, pymongo. A cluster has one primary instance for writes, up to 15 replica instances for reads, and one cluster volume. The cluster volume keeps six copies of the data in three Availability Zones (What is Amazon DocumentDB).

{{ k.fig("docdb-cluster.png", "the primary instance writes to the cluster volume, which has data copies in all three Availability Zones. The replicas read from the same volume. They do not copy data from the primary.") }} {{ k.fig("docdb-endpoints.png", "the cluster endpoint always goes to the primary. The reader endpoint spreads connections over the replicas. Each instance also has its own endpoint.") }}

Lale Market has two instances. The driver connects with readPreference=secondaryPreferred, so the catalog reads go to the replica when it is available, and the primary keeps its capacity for writes. A replica can be a short time behind the primary. For a catalog, this is acceptable.
