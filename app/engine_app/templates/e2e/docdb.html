01The architect's view: where DocumentDB fits

Read this section first. It gives the decision. The sections after it teach how the document model works.

In short: Amazon DocumentDB is a managed document database that is compatible with the MongoDB API. It stores each business object as one JSON-like document. Two documents in one collection can have different fields. You can filter, sort and index on any field, also on fields inside nested objects and arrays.

The key idea is the {{ k.term("aggregate", "aggregate-ddd") }} in the sense of domain design: a group of data that the application reads and writes together. A product with its attributes and tags is one such group. If the shape of the data on disk equals the shape that the screen needs, one read is enough.

The questions that an architect asks, in this order

  1. What does the application read together? Each such group is a candidate for one document.
  2. Do items of one kind have different fields? If yes, a document model saves many optional columns or tables.
  3. Which fields do users filter and sort on? Each frequent filter needs an index. The order of fields in a compound index matters.
  4. Which rules must hold between records? Rules inside one document are easy. Rules between collections belong to the application, or to a relational database.
  5. Does any array grow without an end? Such a list belongs in its own collection or in a different database.
  6. How many writes per second? One writer instance carries the writes of a standard cluster. Beyond that, use elastic clusters or DynamoDB.
  7. Does the team use the MongoDB API now? Then DocumentDB keeps the code and the skills.

Where DocumentDB sits in Lale Market

DocumentDB is the source of truth for the catalog. The home page, the category pages and the product page read from it. The search engine (OpenSearch) holds a copy of the names and descriptions, made by the Seed. Aurora holds a copy of the product id, name, price and stock, because the checkout needs them inside its transactions. In a production shop, a change of a product in DocumentDB would reach the copies as an event, for example from a change stream.

Part 1

The document model of the MongoDB API

Documents, collections, queries, indexes and aggregation.

02Why documents? The folder

An insurance office keeps one paper folder for each customer. The folder holds the policy, the list of insured cars, the addresses, the signed forms. When a customer calls, the clerk takes one folder from the shelf and sees everything. Nobody needs to open five ledgers and match numbers.

{% call k.callout("analogy", "Analogy") %}

A relational database is a set of ledgers: one for customers, one for cars, one for addresses. To see one customer, you open each ledger and match the customer number. A document database is a shelf of folders: everything about one thing is in its folder. The folder is the document. The shelf is the collection.

{% endcall %}

The folder has a price. Sometimes the same fact must appear in many folders, for example the address of an insurance agent. Then each folder has a copy, and a change must update all copies. So a document model works best when each fact belongs to one folder, or when a copy is acceptable.

03The model: documents, collections and identifiers

A {{ k.term("document") }} is a set of field and value pairs, like a JSON object. A value can be a number, a text, a date, an array, or another document (a nested object). Documents of one kind go into a {{ k.term("collection") }}. A collection has no set schema. This is a real product document of Lale Market, as the Engine App reads it with db.products.find_one({ _id: 'P0001' }):

{
  "_id": "P0001",
  "name": "Alpen Kablosuz Kulaklık 1",
  "category": "Elektronik",
  "brand": "Alpen",
  "price": 3373.84,
  "stock": 128,
  "rating": 4.8,
  "attributes": { "renk": "siyah", "garanti_ay": 12, "agirlik_kg": 2.45 },
  "tags": [ "hızlı kargo", "çevreci" ],
  "description": "Alpen markalı siyah kablosuz kulaklık. Elektronik kategorisinde, şık bir ürün."
}
"_id": "P0001"The identifier of the document. The collection owns it: each document has exactly one, and no two documents in the collection can have the same value. DocumentDB always indexes it.
"name", "category", "brand"Text fields at the top level.
"price", "stock", "rating"Number fields. A filter such as { price: { $lt: 1000 } } compares them as numbers.
"attributes": { ... }A nested document. Its fields have no identifier of their own. They belong to this product only. A query reaches them with dot notation: 'attributes.renk'.
"tags": [ ... ]An array of texts. A filter on an array matches when one element matches.

04find: filters, nested fields and projections

A find has two parts. The filter selects documents. The {{ k.term("projection") }} selects the fields that come back.

{% call k.sql("Q1", "Black electronics, cheapest first, four fields") %} 
db.products.find(
  { category: 'Elektronik', 'attributes.renk': 'siyah' },
  { name: 1, price: 1, 'attributes.renk': 1 }
).sort({ price: 1 })
db.productsThe collection products in the current database (shop in Lale Market).
{ category: 'Elektronik', ... }The filter. Each field: value pair is a condition. Two pairs in one object mean AND: both must be true.
'attributes.renk': 'siyah'Dot notation reaches the field renk inside the nested document attributes. The quotes are necessary because of the dot.
{ name: 1, price: 1, 'attributes.renk': 1 }The projection. 1 means "return this field". _id comes back by default. The projection makes the answer smaller, but DocumentDB still reads the full document.
.sort({ price: 1 })Sort the results. 1 is ascending (cheapest first), -1 is descending.
{% endcall %} {% call k.predict("Use the products table. Which documents match { category: 'Elektronik', 'attributes.renk': 'siyah' }? How many documents must DocumentDB examine if no index helps?") %}

One document matches: P0001. P0026 is Elektronik but green (yeşil), and P0044 is black but a book. With no usable index, DocumentDB examines all seven documents. Play the simulation to see each test.

{% endcall %} {{ k.sim("scan", "A filter with no usable index: COLLSCAN") }}

Operators start with a dollar sign, so DocumentDB can tell them from field names. Examples: $gt and $gte (greater than, greater or equal), $in (one of a list), $exists (the field is in the document or not). A filter can combine them: { 'attributes.garanti_ay': { $gte: 24 }, rating: { $gte: 3.5 } }.

05Indexes: what DocumentDB reads to answer

Without an index, DocumentDB must test each document. This is a {{ k.term("collection scan") }} (COLLSCAN). An index keeps the values of one or more fields in a sorted tree, and each entry points to a document. With an index, DocumentDB goes straight to the matching documents. The plan shows the stages IXSCAN and FETCH.

{{ k.fig("docdb-btree.png", "each node keeps its keys in sorted order. A search goes from the root to one leaf and reads one node on each level. An index on { category, rating } sorts first by category, then by rating inside each category.") }}

Lale Market has four indexes on products (from the Seed in engines/docdb.py):

db.products.create_index([("category", 1), ("rating", -1)])   # compound: category, then rating high to low
db.products.create_index([("attributes.renk", 1)])           # a nested field
db.products.create_index([("rating", -1)])                   # top rated products on the home page
# and the automatic index on _id
{% call k.predict("The index { category: 1, rating: -1 } exists. A query asks for the books (Kitap), best rating first. How many index entries does DocumentDB read, and does it need to sort?") %}

It reads the two Kitap entries and one more entry, which shows that the Kitap range is over. It does not sort, because the index already has the Kitap entries in rating order. It examines two documents.

{% endcall %} {{ k.sim("index", "The compound index finds the books in rating order") }}

The order of fields in a compound index matters. { category: 1, rating: -1 } helps "books, best first". It does not help "all products with rating above 4.5", because the tree sorts by category first. For that question, Lale Market has the separate index { rating: -1 }. Each index also costs work: every insert and every change of an indexed field must update the index.

To see the plan of a query, add .explain('executionStats'). The Lale Market category page shows two numbers from it: "docs examined" and "returned". With the index, the two numbers are equal. With the "Collection scan" experiment, "docs examined" is the full collection (200).

06Aggregation: a pipeline of stages

An {{ k.term("aggregation pipeline") }} is a list of stages. Each stage takes documents, changes them, and gives them to the next stage, like stations on a production line. The home page of Lale Market uses $group to count the products of each category on the server.

{% call k.sql("Q2", "How many products have each tag, and their average price") %} 
db.products.aggregate([
  { $unwind: '$tags' },
  { $group: { _id: '$tags', products: { $sum: 1 }, avg_price: { $avg: '$price' } } },
  { $sort: { products: -1 } }
])
{ $unwind: '$tags' }For each element of the array tags, make one copy of the document with that one tag. A product with two tags becomes two documents. '$tags' with a dollar sign means "the value of the field tags".
{ $group: { _id: '$tags', ... } }Put the documents with the same tag into one group. _id of the output is the tag.
products: { $sum: 1 }For each document in the group, add 1: this counts the documents.
avg_price: { $avg: '$price' }The average of the field price inside the group.
{ $sort: { products: -1 } }Put the group with the most products first.
{% endcall %} {% call k.predict("Each of the seven products in the table has exactly two tags. How many documents leave the $unwind stage? Which tag has the most products?") %}

14 documents (7 × 2). Count the tags in the table: "çevreci" appears in P0001, P0044, P0095 and P0179, so 4 times. "yeni" also appears 4 times (P0005, P0026, P0095, P0142). Then "çok satan" 3 times.

{% endcall %} {{ k.sim("pipeline", "$unwind, then $group, then $sort") }} {{ k.quiz("doc-q2", "Each of 200 products has exactly 2 tags. 07Design: embed or reference?

The main design question of a document database is where each piece of data lives:

  • Embed: put the data inside the parent document. One read returns all of it. Use it when the data belongs to one parent, is small, and is read with the parent.
  • Reference: keep the data in its own collection, and store its _id in the parent or in the child. Use it when the data is shared, large, or grows without an end.
DataChoiceWhy
Attributes and tags of a productEmbedSmall, always read with the product, belongs to one product only.
The brand profile (logo, country, contact)ReferenceShared by many products. A copy in each product would need many updates.
Reviews of a productReference, and embed the newest fiveThousands of reviews would make the document large. The page shows only a few.
Orders of a customerNot in DocumentDB (Lale Market uses Aurora)The list grows without an end, and an order needs rules with the stock.

When a change must touch several documents together, DocumentDB 4.0 and later supports transactions "across multiple documents, statements, collections, and databases" (Transactions in Amazon DocumentDB). A good document design needs them rarely, because most changes touch one document.

{% call k.callout("warn", "Common mistake") %}

Do not embed a list that grows with time, such as all orders or all page views. The document becomes larger with each write, and each read returns data that the page does not need. Lale Market keeps page views in Keyspaces, one row per event.

{% endcall %}

08Running a document database yourself, and what DocumentDB changes

A self-managed MongoDB deployment is usually a replica set: one primary server and two or more secondary servers. Each server keeps a full copy of the data on its own disk, and the secondaries copy each change from the primary. You install the servers, watch the copies, replace a failed disk, make the disks larger, take backups and apply updates.

Amazon DocumentDB keeps the MongoDB API but separates compute and storage, like Aurora. A cluster "consists of 0 to 16 instances and a cluster storage volume". "All writes are done through the primary instance. All instances (primary and replicas) support reads." The storage layer "replicates six copies of your data across three AWS Availability Zones" (What is Amazon DocumentDB).

{{ k.fig("docdb-cluster.png", "the primary instance writes to the cluster volume, which has data copies in all three Availability Zones. The replicas read from the same volume. They do not copy data from the primary.") }} {{ k.fig("docdb-endpoints.png", "the cluster endpoint always goes to the primary. The reader endpoint spreads connections over the replicas. Each instance also has its own endpoint.") }}
TaskSelf-managed MongoDB replica setAmazon DocumentDB

Some limits change a design (DocumentDB quotas):

  • A document can be up to 16 MiB.
  • A document can nest up to 200 levels.
  • A collection can have up to 64 indexes.

09DocumentDB in Lale Market

  • One instance-based cluster with two instances: a primary and one replica.
  • The database shop has one collection, products, with 200 documents and four indexes.
  • The DocumentDB Engine App connects with the Python driver pymongo, with TLS on port 27017 and a password from AWS Secrets Manager.
  • The driver uses readPreference=secondaryPreferred: catalog reads go to the replica when it is available, and the primary keeps its capacity for writes. A replica can be a short time behind the primary. For a catalog, this is acceptable.
  • The category page has the "Collection scan" experiment, and the product page has the projection experiment.
