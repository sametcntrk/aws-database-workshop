01The architect's view: where ElastiCache fits

Read this section first. It gives the decision. The sections after it teach how Valkey works.

In short: Amazon ElastiCache keeps small, hot data in memory and answers in microseconds. It runs the Valkey, Redis OSS or Memcached engine. Use it for data that many requests read or change each second, and for data that you can rebuild or can lose. Keep the official record of your business in a durable database.

Memory is fast but expensive per GB, and it is the first layer to lose data in a failure. So the main question of an architect is not "is it fast?" but "what happens if this data is gone?" If the answer is "we rebuild it" or "nobody cares after an hour", the data can live in ElastiCache.

The questions that an architect asks, in this order

  1. What happens if this data disappears? If the business loses money or trust, keep the record elsewhere and use ElastiCache only as a copy.
  2. How old can the data be? This number is the TTL of a cache entry.
  3. How do you find the data? Always by a key: good. By any field: a different engine.
  4. Which data type matches the question? A counter, a hash, a sorted set or a list. The right type makes the question one command.
  5. How many clients change the same value? If many, use one atomic command, never a read and a later write.
  6. How large is the hot data? The working set must fit in memory. ElastiCache Serverless grows the memory for you, and you pay for it.
  7. Do you need a durable log? Node-based Valkey clusters (version 9.0 and higher) can keep a Multi-AZ transactional log. That changes the decision for some data.

Where ElastiCache sits in Lale Market

Lale Market uses one ElastiCache Serverless cache with the Valkey engine for four jobs:

  • the flash deal: a hash and a stock counter,
  • the session of each visitor: a hash with a TTL,
  • the live leaderboard: a sorted set,
  • two counters: orders today and active visitors.

Every piece can be rebuilt. The Seed of the Admin Console builds the leaderboard again from the orders in Aurora. The orders themselves never live only in memory.

Valkey: the in-memory data store

Keys, data types, atomic commands, caching and expiry.

02Why memory is fast, and what it costs

A computer keeps data on layers of storage. The layers near the processor are fast, small and expensive. The layers far from it are slow, large and cheap. A disk-based database keeps its data on SSDs and holds the busy part in memory. An {{ k.term("in-memory database") }} keeps all of its data in RAM.

{{ k.fig("elasticache-memory-hierarchy.png", "random access memory (RAM) is in the middle of the pyramid: \"fast, affordable\" and \"power on, very short term\". Disks are lower: larger and slower. Valkey keeps the full data set in RAM.") }} {% call k.callout("analogy", "Analogy") %}

Memory is the counter of a shop. The cashier reaches what is on the counter in one second. The stockroom (the disk) holds much more, but each trip takes time. A shop puts on the counter only what customers ask for each minute. And if the counter falls over, the stockroom still has the goods. That is why a cache needs a database behind it.

03The model: keys and typed values

Valkey is a {{ k.term("key-value store") }}. Each entry has a key (a text) and a value. Unlike DynamoDB, each value has a data type, and each type has its own commands. These are the real keys of Lale Market (the values are examples):

Who owns which identifier: the application owns the key names. Valkey has no tables, so the colon in lm:deal:stock is only a naming convention. lm: marks the keys of Lale Market. 04Atomic commands: the last piece

Valkey uses "a mostly single threaded design for command execution" (Valkey: latency). The commands of all clients go into one line, and Valkey runs them one after the other. So a single command is {{ k.term("atomic") }}: no other command can run in the middle of it. Two commands of one client are not atomic together: other clients' commands can run between them.

{% call k.callout("analogy", "Analogy") %}

A ticket office has one clerk and one queue. Each customer asks one question at a time. If you ask "how many seats are left?" and then go back to the end of the queue to say "I take one", other customers can buy the last seat in between. If you say "give me one seat if there is one", the clerk checks and sells in one answer. DECR is that second sentence.

{% endcall %} {% call k.predict("One piece is left. Two buyers run GET, then SET (value - 1). In the worst order of their commands, how many pieces does the shop sell?") %}

Two. If both GETs run before the first SET, both buyers see 1, and both write 0. Play the first simulation. Then play the second one, where each buyer sends one DECR.

{% endcall %} {{ k.sim("race_naive", "Read, then write: two buyers, one piece") }} {{ k.sim("race_atomic", "DECR: two buyers, one piece") }}

The real flash deal page of Lale Market has a Load Simulation with 300 buyers and 10 pieces. In the "Read, then write" mode, it usually sells more than 10. The number changes from run to run, because it depends on the timing. That is the nature of a {{ k.term("race condition") }}: a test can pass and production can fail.

05Sorted sets: a ranking that is always ready

A {{ k.term("sorted set") }} holds unique members, and each member has a number, the score. Valkey keeps the members in score order at each write. Adding or changing a member is O(log N), where N is the number of members (Valkey: sorted sets). So "the top 10" needs no sort at read time.

{% call k.sql("Q2", "Add the total of an order to a customer, then read the top three") %}

ZREVRANGE lm:leaderboard 0 2 WITHSCORES
ZINCRBY lm:leaderboard 20000 C00003Add 20000 to the score of the member C00003. If the member does not exist, Valkey creates it with that score. The checkout of Lale Market sends this command with the order total.
ZREVRANGE lm:leaderboard 0 2Return the members at positions 0 to 2, from the highest score down. REV means reverse: highest first.
WITHSCORESReturn the score after each member.

06Cache-aside: memory in front of a database

The most common use of ElastiCache is a cache in front of a slower database. The usual pattern is {{ k.term("cache-aside") }}:

  1. The application looks for the key in the cache.
  2. On a hit, it returns the value. The database does no work.
  3. On a miss, it reads the database, writes the value into the cache with a TTL, and returns it.
{% call k.predict("Six page views ask for P0001, P0044, P0001, P0001, P0095, P0044. The cache is empty at the start. How many views go to the database?") %}

Three: the first view of each product. The other three views are hits. Play the simulation to check.

{% endcall %} {{ k.sim("cache", "Cache-aside with six page views") }}

The price of a cache is old data. When a price changes in the database, the cache can show the old price until the TTL ends. The application can also delete the cache key when it changes the database. Either way, the architect decides how old the data may be, and writes it down.

07TTL: data that deletes itself

Each key can have a {{ k.term("TTL") }} (time to live) in seconds. When it gets to zero, Valkey deletes the key. The session of each Lale Market visitor is a hash with a TTL of 1,800 seconds (30 minutes). Each page view sends EXPIRE again, so an active session stays, and an abandoned session goes away with no cleanup job.

{% call k.sql("Q3", "Write a session and give it 30 minutes to live") %} 
HSET lm:session:7f3a persona C00001 last_page /cart
EXPIRE lm:session:7f3a 1800
TTL lm:session:7f3a
HSET lm:session:7f3a persona C00001 last_page /cartWrite two fields into the hash of this visitor. HSET creates the hash if it does not exist.
EXPIRE lm:session:7f3a 1800Set the time to live to 1,800 seconds. A new EXPIRE starts the countdown again.
TTL lm:session:7f3aReturn the seconds that are left. -2 means that the key does not exist.

Amazon ElastiCache: the AWS service

Valkey with no nodes to operate.

08Running Valkey yourself, and ElastiCache Serverless

When you run Valkey yourself, you must select servers with enough memory and set up replicas in other data centers. You must split the keys over shards when the data grows. You also watch the memory, plan failover and update the software. A full memory makes Valkey refuse writes or delete keys, so the size planning matters.

With ElastiCache Serverless, you "simply provide a name for your cache and you receive a single endpoint". It "continuously monitors the memory, compute, and network bandwidth utilization of your cache and scales both vertically and horizontally". It "automatically replicates your data across multiple Availability Zones" (How ElastiCache works).

{{ k.fig("elasticache-serverless.png", "the application in each Availability Zone connects to a VPC endpoint. The proxy nodes in the service VPC send each request to the cache nodes. The application does not know how many cache nodes exist.") }}
TaskValkey on your own serversElastiCache Serverless
Memory sizeYou select it and add shards before it is full.ElastiCache grows and shrinks it. You pay for GB-hours of data stored.
Copies in several data centersYou set up replicas and failover.Replication across Availability Zones is automatic.
Client configurationThe client must know the shards and follow changes.One endpoint. A proxy layer hides the shards.
UpgradesYou plan and run them.Minor and patch versions with no availability impact.
Cost modelServers per hour.Data stored (GB-hours) and ElastiCache Processing Units (ECPUs). A simple GET or SET of up to 1 KB uses 1 ECPU.

ElastiCache Serverless runs Valkey in cluster mode, and only clients with TLS can connect. In cluster mode, the keys spread over shards by a hash of the key name. A command that uses several keys works only when all its keys are in one shard. That is why each Lale Market command uses one key.
