00What you will learn

Lale Market keeps its fastest-changing data in Amazon ElastiCache Serverless with the Valkey engine. This data is the flash deal stock, the sessions, the live leaderboard and some counters. Each Visitor reads this data on each page. Some values change many times each second.

After this tutorial, you can do these tasks:

  1. Explain why a read from memory is much faster than a read from disk, and what this costs.
  2. Select the Valkey data type for a job: string, counter, hash or sorted set.
  3. Show, with a measurement, why one atomic command is correct and "read, then write" is not.
  4. Use a TTL to make data delete itself.
  5. Say which data can live only in a cache, and which data needs a database of record.

01Why memory is fast

A computer keeps data on layers of storage. The layers near the CPU are fast, small and expensive. The layers far from the CPU are slow, large and cheap. A disk-based database keeps its data on SSDs and holds the busy part in memory. An {{ k.term("in-memory database") }} keeps all of its data in RAM.

{{ k.fig("elasticache-memory-hierarchy.png", "random access memory (RAM) is in the middle of the pyramid: \"fast, affordable\" and \"power on, very short term\". Disks are lower: larger and slower. Valkey keeps the full data set in RAM.") }}

The consequence for you: a GET from Valkey inside the VPC takes well under a millisecond in the Behind-the-scenes panel of Lale Market. The price is the capacity. RAM is more expensive per GB than SSD, so you keep small, hot data in memory, not your full history.

{% call k.callout("analogy", "Analogy") %}

Memory is the counter of a shop. The cashier reaches what is on the counter in one second. The stockroom (the disk) holds much more, but each trip takes time. You put on the counter the items that customers ask for each minute, not the full stock.

{% endcall %}

02The model: keys and typed values

Valkey is a {{ k.term("key-value store") }}. Each entry has a key (a text) and a value. Unlike DynamoDB, the value has a data type, and each type has its own commands. Lale Market uses four types. These are the real keys (from META.model of the Engine App):

keytypeexample valuecommands that Lale Market uses
lm:dealhashproduct_id → P0001, name → Alpen Kablosuz Kulaklık 1, price → 2024.30, ends_at → 1793...HGETALL, HSET
lm:deal:stockstring (counter)49GET, DECR, INCR
lm:session:<visitor>hash with a TTLpersona → C00001, last_page → /cartHSET, EXPIRE, HGETALL, TTL
lm:leaderboardsorted setC00001 → 1200345.50, C00002 → 980100.10, ...ZINCRBY, ZREVRANGE
lm:activesorted set<visitor> → <last seen, Unix time>ZADD, ZCOUNT

The colon in the key names is a convention, not a feature. Valkey has no tables. lm: marks the keys of Lale Market, and the rest names the thing.

A hash keeps several fields under one key. HINCRBY changes one field without a read and a write of the full object.

03Atomic commands: the flash deal

Valkey uses "a mostly single threaded design for command execution" (Valkey: latency). The commands of all clients go into one line, and Valkey runs them one after the other. So a single command is {{ k.term("atomic") }}: no other command can run in the middle of it.

The flash deal has 10 pieces and 60 buyers. Two programs can sell the pieces:

"Read, then write" (two commands)"DECR" (one command)
 
v = GET stock          # 1st command
if v > 0:
    SET stock v - 1    # 2nd command
    sell()
 
left = DECR stock      # one command
if left >= 0:
    sell()
else:
    INCR stock         # give it back
{% call k.predict("Twenty buyers run at the same time. With \"Read, then write\", how many pieces can the shop sell from a stock of 10? With DECR?") %}

With "Read, then write": more than 10 is possible. Between one buyer's GET and SET, other buyers run their GET and see the same value. Each of them writes "v - 1", so several sales take away only one piece. With DECR: exactly 10. Each DECR reads and changes the value in one step. Run V7 to measure it.

{% endcall %} {% call k.query("elasticache", "V7", "Sell 10 pieces to 60 buyers, two ways") %} 
SET lm:tut:race:naive:<you> 10      → 60 buyers, 20 threads: GET, then SET value - 1
SET lm:tut:race:atomic:<you> 10     → 60 buyers, 20 threads: DECR, and INCR if below 0

Look at "pieces sold". The naive mode usually sells more than 10. The result changes from run to run, because it depends on the timing of the threads. That is the nature of a {{ k.term("race condition") }}: it is not always visible, so a test can pass and production can fail.

{% endcall %} {% call k.query("elasticache", "V3", "INCR as a counter") %} 
INCR lm:tut:visits
INCR lm:tut:visits
INCR lm:tut:visits
INCRBY lm:tut:visits 10

INCR returns the new value. Lale Market counts the orders of the day with INCR lm:orders:today. Many Engine App threads can count at the same time, and no count is lost.

{% endcall %} {{ k.quiz("ec-q1", "Why is DECR safe for the flash deal stock, but GET then SET is not?", ["DECR reads and writes in one command", "DECR stores the value on a disk", "DECR is faster than two commands", "DECR locks the key for one second"], 0, "Valkey runs one command at a time. Between two separate commands, other clients can run theirs.") }}

04Sorted sets: a leaderboard that is always sorted

A {{ k.term("sorted set") }} holds unique members, and each member has a number, the score. Valkey keeps the members in score order at each write. Adding or changing a member is O(log N), where N is the number of members (Valkey: sorted sets). So "the top 10" is ready at any time, with no sort at read time.

The Lale Market leaderboard has one member per customer, with the revenue as the score. Each checkout sends ZINCRBY lm:leaderboard <order total> <persona>.

{% call k.query("elasticache", "V5", "Build a small leaderboard and move one member") %} 
ZADD lm:tut:board 36708.47 Ayşe 98210.10 Mert 1599.41 Elif 45120.00 Lukas 27300.55 Zeynep
ZINCRBY lm:tut:board 20000 Elif
ZREVRANGE lm:tut:board 0 2 WITHSCORES      # top 3, highest score first
ZREVRANK lm:tut:board Elif                 # 0-based position from the top
{% endcall %} {% call k.query("elasticache", "V8", "The real Lale Market leaderboard") %} 
ZREVRANGE lm:leaderboard 0 4 WITHSCORES
ZCARD lm:leaderboard
{% endcall %} {{ k.quiz("ec-q2", "Elif has score 1,599.41 and gets ZINCRBY 20000. In V5, what is her new place?", ["Second place", "Third place", "Fourth place", "Fifth place"], 3, "21,599.41 is below Mert (98,210.10), Lukas (45,120.00), Ayşe (36,708.47) and Zeynep (27,300.55). 05TTL: data that deletes itself

Each key can have a {{ k.term("TTL") }} (time to live) in seconds. When it gets to zero, Valkey deletes the key. The session of each Visitor is a hash with a TTL of 30 minutes. Each page view sends EXPIRE again, so an active session stays, and an abandoned session goes away with no cleanup job.

{% call k.query("elasticache", "V6", "Watch a key expire") %} 
SET lm:tut:short "I expire soon" EX 5
TTL lm:tut:short        # at 0, 2, 4 and 6 seconds
EXISTS lm:tut:short

This query takes about 6 seconds, because it waits between the reads. TTL returns -2 when the key does not exist.

{% endcall %}

06ElastiCache Serverless

With ElastiCache Serverless, you do not select nodes. You get one endpoint. A proxy layer receives the connections and sends each command to a cache node. ElastiCache "continuously monitors the memory, compute, and network bandwidth utilization of your cache and scales both vertically and horizontally". It also replicates the data across multiple Availability Zones (How ElastiCache works).

{{ k.fig("elasticache-serverless.png", "the application in each Availability Zone connects to a VPC endpoint. The proxy nodes in the service VPC send each request to the cache nodes. The application does not know how many cache nodes exist.") }}

The cost has two parts: the data stored (GB-hours) and ElastiCache Processing Units (ECPUs). A simple GET or SET of up to 1 KB uses 1 ECPU. Serverless runs Valkey in {{ k.term("cluster mode") }}. In cluster mode, the keys spread over shards by a hash of the key name. A command that uses several keys works only when all of its keys are in one shard. This is why each Lale Market command uses one key.

07Cache or database of record?

Many apps use ElastiCache as a cache in front of a database. The common pattern is {{ k.term("cache-aside") }}:

  1. The app looks for the key in the cache.
  2. On a hit, it returns the value. On a miss, it reads the database.
  3. It writes the value into the cache with a TTL, and returns it.

Lale Market uses Valkey in a second way: as the main store of short-lived, rebuildable data. The leaderboard comes from the orders. The Seed step of the Admin Console builds it again from the order history. The orders themselves stay in Aurora.

{{ k.quiz("ec-q3", "Which Lale Market data must NOT exist only in ElastiCache?", ["The session of a Visitor", "The flash deal countdown", "The committed orders of customers", "The number of active Visitors"], 2, "Orders are the record of what the shop sold. They need durable storage, constraints and transactions. The other three can be rebuilt or are short-lived.") }}
