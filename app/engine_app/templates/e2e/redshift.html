01The architect's view: where Redshift fits

Read this section first. It gives the decision. The sections after it teach how a warehouse works.

In short: Amazon Redshift is a data warehouse. It answers SQL questions over very many rows: "revenue per month per category for two years", "the best 100 customers by city". It stores each column separately, skips blocks that cannot match, and splits the work across many slices that run in parallel. It is the place for reports and analytics, not for the clicks of the shop.

The key idea is {{ k.term("OLAP") }} (online analytical processing): few queries, each one reads millions of rows but only a few columns. The checkout does {{ k.term("OLTP") }}: many queries, each one reads or writes a few complete rows.

The questions that an architect asks, in this order

  1. Is it a report or a transaction? Reports go to the warehouse. Transactions stay in the operational database.
  2. How fresh must the report be? Seconds point to zero-ETL. Hours or a day allow a batch load with COPY.
  3. Which columns and which filters do the reports use? They decide the sort key.
  4. Which tables join, and on which column? They decide the distribution key. With AUTO, Redshift decides.
  5. Is the load steady or in bursts? Bursts and idle nights point to Redshift Serverless. A steady, high load can use a provisioned cluster.
  6. Must the data stay in S3? Then query it with external tables, or with Amazon Athena.

How a columnar data warehouse works

Facts and dimensions, column storage, zone maps and parallel slices.

02Facts and dimensions: the star schema

A warehouse usually stores events in one large {{ k.term("fact table") }}: one row for each sale, with numbers (quantity, amount) and keys. Around it are {{ k.term("dimension table") }}s: customers, products, dates, stores. A dimension describes the keys of the fact table. The drawing looks like a star.

{{ k.fig("redshift-star-schema.png", "a star schema. One fact table is in the middle, and four dimension tables are around it.") }}

Lale Market keeps the history in one flat table sales. It already contains the city of the customer and the category of the product, so most reports need no join. These are eight example rows:

{{ k.sample("rs_sales", "sales: eight example rows", key=["order_id", "product_id"], ref=["customer_id"]) }}

Identifiers: Aurora owns the order id, the customer id and the product id. The sales table borrows all three. The pair of order_id and product_id identifies one order line. Redshift does not enforce primary keys or foreign keys. It accepts them as information for the planner, so the load process must keep the ids correct.

{% call k.sql("Q1", "The report of the Lale Market admin page") %} 
SELECT category AS category, count(DISTINCT order_id) AS orders, sum(qty) AS units, sum(amount) AS revenue
FROM sales GROUP BY 1 ORDER BY revenue DESC LIMIT 24
SELECT category AS categoryThe group label. The page can also group by month or by city.
count(DISTINCT order_id) AS ordersThe number of different orders in the group. One order can have several lines.
sum(qty), sum(amount)The units and the revenue of the group.
GROUP BY 1Group by the first column of the SELECT list.
ORDER BY revenue DESC LIMIT 24The groups with the highest revenue first, at most 24.

It reads category, order_id, qty and amount. It does not need order_date, customer_id, city and product_id, four of the eight columns.

03Column storage: read only what the query needs

A row store, like PostgreSQL, puts each complete row in a disk block. That is good for the checkout: one order is one row, and the database reads or writes it in one place. A {{ k.term("column store") }} puts the values of one column together in a block. A report that needs two columns reads two kinds of blocks and leaves the others on disk.

{% call k.callout("analogy", "Analogy") %}

Think of a large spreadsheet printed on paper. A row store prints one customer per page with all the fields. To add up one column, you must turn every page. A column store prints one column per page. To add up the amounts, you take the amount page and nothing else.

{% endcall %} {{ k.fig("redshift-row-storage.png", "row storage. Each disk block holds complete rows with all their columns.") }} {{ k.fig("redshift-column-storage.png", "column storage. One disk block holds the values of one column for many rows.") }} {{ k.sim("rowcol", "SELECT category, sum(amount): row store and column store") }}

A second gain is compression. A column holds values of one type and often with repeats, for example the same city many times. Redshift selects a compression encoding for each column, so the same data uses fewer blocks.

{{ k.quiz("rs-q1", "A table has 50 columns. A query reads 2 of them over all rows. Approximately what share of the data does a column store read?", ["All of it", "About half", "About 2 of 50 columns", "Only the first row"], 2, "A column store reads the blocks of the 2 columns. The blocks of the other 48 columns stay on disk.") }}

04Sort keys and zone maps: skip the blocks that cannot match

Redshift stores each column in 1 MB blocks. For each block, it keeps the smallest and the largest value in memory. This is the {{ k.term("zone map") }}. Before it reads a block, Redshift compares the filter of the query with the zone map. If the range of the block cannot match, Redshift skips it (Choose the best sort key).

The zone map helps only if the values in each block are close together. The {{ k.term("sort key") }} does this: it stores the rows on disk in the order of one or more columns.

{% call k.sql("Q2", "A report for one month") %} 
SELECT category, sum(amount) AS revenue
FROM   sales
WHERE  order_date BETWEEN '2026-03-01' AND '2026-03-31'
GROUP  BY category;
WHERE order_date BETWEEN ... AND ...A range filter on the sort key column. Redshift compares it with the minimum and the maximum of each block.
GROUP BY categorySum the amounts of the remaining rows per category.
{% endcall %} {{ k.sim("zonemap", "March: sorted blocks and unsorted blocks") }} {% call k.callout("analogy", "Analogy") %}

A library shelf with books sorted by year has a label on each shelf: "1990 to 1995". To find books from 1993, you go to one shelf. If the books are in random order, every shelf has books from all years, and the labels do not help.

05Slices and distribution: many workers in parallel

Redshift is an {{ k.term("MPP") }} (massively parallel processing) system. It splits each table across {{ k.term("slice") }}s. Each slice scans its own part, and Redshift combines the results. When a query joins two tables, the matching rows must be on the same slice. If they are not, Redshift moves rows over the network first. The {{ k.term("distribution style") }} of a table decides where its rows go.

StyleWhere the rows goGood for
KEYBy the value of one column, the DISTKEY. Equal values are on the same slice.A large table that joins on that column.
EVENIn turn, with no regard to the values.A table that does not join.
ALLA complete copy on every node.A small dimension table.
AUTORedshift selects and changes the style as the table grows. It is the default.Most tables.

If one person must look up names on a list that another person has, they must pass papers across the table. That is slow. Give each person the papers and the list for the same names.

Amazon Redshift: the AWS service

Serverless capacity, managed storage, and zero-ETL from Aurora.

06Redshift Serverless and managed storage

Redshift Serverless measures capacity in Redshift Processing Units (RPUs). One RPU provides 16 GB of memory, and the default base capacity is 128 RPUs (Compute capacity for Redshift Serverless). The capacity scales up and down with the load. You pay for the RPU-hours that the workloads use, so an idle night costs no compute.

The data lives in Redshift managed storage, apart from the compute. A provisioned cluster has a leader node that plans the queries and compute nodes that run them, as the architecture image in section 01 shows.

07Zero-ETL from Aurora

The AWS documentation describes the zero-ETL integration as a managed solution. It makes transactional data available in Redshift "within seconds of being written" (Aurora zero-ETL integrations). You create the integration once. In Redshift, one statement creates a database from it:

CREATE DATABASE aurora_liveA new database in Redshift. Its tables are the copies of the Aurora tables.
FROM INTEGRATION '<integration id>'The zero-ETL integration that AWS runs between the Aurora cluster and the Redshift namespace.
DATABASE shopThe database in Aurora that the integration copies.
{% endcall %} {% call k.sql("Q4", "The live report, on the zero-ETL copy") %} 
SELECT p.category AS category, count(DISTINCT o.order_id) AS orders, sum(oi.qty) AS units, sum(oi.qty * oi.unit_price) AS revenue
FROM aurora_live.public.orders o
JOIN aurora_live.public.order_items oi ON oi.order_id = o.order_id
JOIN aurora_live.public.products p ON p.product_id = oi.product_id
JOIN aurora_live.public.customers c ON c.customer_id = o.customer_id

08Redshift in Lale Market

  • One Redshift Serverless workgroup in the data subnets. The Redshift Engine App connects on TLS port 5439 with a password from Secrets Manager.
  • The history table sales has DISTKEY customer_id and SORTKEY order_date. The Seed loads it with one row for each order line that is not cancelled.
  • The database aurora_live is the zero-ETL copy of the Aurora database shop. An order from the checkout appears there within seconds, with no pipeline code.
  • The admin page "Sales reports" groups by month, category or city, from the history or from the live copy.
  • Redshift keeps no visitor data of its own. When Aurora deletes visitor orders, zero-ETL deletes the copies.
