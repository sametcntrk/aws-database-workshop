01The architect's view: where OpenSearch fits

Read this section first. It gives the decision. The sections after it teach how a search engine works.

In short: Amazon OpenSearch Service runs OpenSearch, a search and analytics engine. It finds documents by the words in them and ranks them by relevance. It accepts typos, counts results by category in the same request, and searches by location. It is usually a fast copy of data whose source of truth lives in another database.

The key structure is the {{ k.term("inverted index") }}. A database index answers "where is the row with this value?". An inverted index answers "which documents contain this word?".

The questions that an architect asks, in this order

  1. Where is the source of truth? Decide how changes reach the index: an event, a stream, a zero-ETL integration, or a rebuild.
  2. How old may the search results be? Seconds are normal for a copy.
  3. Which language and which spelling problems? They decide the analyzers.
  4. Which filters and counts does the page show? They decide the keyword fields and the aggregations.
  5. How much data, and how many queries per second? They decide the shards, the replicas and the instance sizes, or the use of OpenSearch Serverless.
  6. Is it search or log analytics? Logs grow every day and need a policy that deletes old indexes.

Where OpenSearch sits in TDS Academy Market

The catalog lives in DocumentDB. The Seed copies six fields of each product into the index products: the name, the description, the category, the brand, the price and the rating. It also copies the stores into the index stores. The search page, the header suggestions and the store finder read only from OpenSearch. In a production shop, each product change would reach the index as an event, so the index stays a few seconds behind the catalog.

How a search engine works

Analyzers, the inverted index, scores, fuzziness, facets and geo search.

02Why a search engine? The index at the back of a book

A database finds a row by a value that you know exactly: a product id, a price. People search differently. They type some words, in any order, with typos, without Turkish letters. To find "Kablosuz Kulaklık" for the query "kulaklik kablosuz", the engine must compare words, not whole values.

{% call k.callout("analogy", "Analogy") %}

The index at the back of a book lists each important word and the pages where it appears. To find pages about "transaction", you do not read the book. You look up one word and get a list of pages. An inverted index is this list for every word of every document.

{% endcall %}

Identifiers: the catalog (DocumentDB) owns the product id. The index borrows it as the document _id, so a search result can link to the product page. OpenSearch replaces a document with the same _id, so a repeated load does not create duplicates.

03Analyzers: from text to tokens

Before OpenSearch stores a text field, an {{ k.term("analyzer") }} splits the text into {{ k.term("token") }}s and changes each token. The same analyzer runs on the query, so the two sides match. TDS Academy Market defines a custom analyzer for Turkish names (from engines/opensearch.py):

{% call k.sql("M1", "The analyzer and the mapping of the products index") %} 
"settings": {"analysis": {
  "filter":   {"tr_lower": {"type": "lowercase", "language": "turkish"}},
  "analyzer": {"tr_folded": {"tokenizer": "standard", "filter": ["tr_lower", "asciifolding"]}}}},
"mappings": {"properties": {
  "name":     {"type": "text", "analyzer": "tr_folded", "fields": {"std": {"type": "text", "analyzer": "standard"}}},
  "category": {"type": "keyword"},
  "price":    {"type": "float"}}}
"tokenizer": "standard"Split the text into words at spaces and punctuation.
"tr_lower": lowercase, turkishLowercase with Turkish rules: "I" becomes "ı" and "İ" becomes "i".
"asciifolding"Change letters to their plain forms: "ı" becomes "i", "ş" becomes "s", "ğ" becomes "g".
"name": text, tr_foldedThe field name uses this analyzer for full-text search.
"fields": {"std": ...}A second copy of the same field, name.std, with the standard analyzer. The search page uses it for the "standard" experiment.
"category": keywordA keyword field is not analyzed. It keeps the exact value, so it is right for filters and counts.
{% endcall %} {{ k.sim("analyze", "One name, two analyzers") }}

You can see the tokens of any text with the _analyze API (OpenSearch: Text analysis).

04The inverted index and the relevance score

The OpenSearch documentation defines it: "An inverted index maps words to the documents in which they occur" (Intro to OpenSearch). The list of documents for one token is its {{ k.term("posting list") }}.

{% call k.sql("Q1", "A search on the product name") %} 
GET products/_search
{ "query": { "match": { "name": "kablosuz kulaklik" } } }
GET products/_searchSearch the index products.
"match": { "name": ... }A full-text query on the field name. OpenSearch analyzes the query text with the analyzer of the field (tr_folded).
"kablosuz kulaklik"Two tokens. By default, a document matches if it contains at least one of them. Documents with both tokens get a higher score.
{% endcall %} {% call k.predict("Use the six documents. Which documents match \"kablosuz kulaklik\", and which ones come first?") %}

P0001, P0031 and P0081 contain both tokens, so they match with the highest scores. No other document contains either token.

{% endcall %} {{ k.sim("inverted", "Look up two tokens in the inverted index") }}

"OpenSearch uses the BM25 ranking algorithm to calculate document relevance scores" (Intro to OpenSearch). In simple words, three rules apply. A token that appears in few documents counts more. A token that appears often in a short field counts more. More matching tokens give a higher score.

05Fuzziness: a search that accepts typos

The {{ k.term("edit distance") }} between two words is the number of single-letter changes that turn one into the other. OpenSearch counts with the Damerau–Levenshtein distance. Each of these changes counts as one edit: an added letter, a deleted letter, a changed letter, or two swapped neighbor letters (OpenSearch: Fuzziness). With fuzziness: AUTO, the number of allowed edits depends on the length of the term. The documentation example: a term of 6 characters allows 2 edits.

{% call k.sql("Q2", "A search with typo tolerance") %} 
GET products/_search
{ "query": { "match": { "name": { "query": "kulaklk", "fuzziness": "AUTO" } } } }
"query": "kulaklk"The text that the shopper typed. One letter is missing.
"fuzziness": "AUTO"Also accept index terms that are a few edits away. The number depends on the length of the term.

06Filters and facets in the same request

A search page shows the hits and, at the left, counts by category and by price range. These counts are {{ k.term("aggregation") }}s. OpenSearch calculates them in the same request. This is the real request of the TDS Academy Market search page:

{% call k.sql("Q3", "Hits, a category filter and two aggregations") %} 
GET products/_search
{ "query": { "bool": {
    "must":   [ { "multi_match": { "query": "kablosuz kulaklik", "fields": ["name^3", "description"], "fuzziness": "AUTO" } } ],
    "filter": [ { "term": { "category": "Elektronik" } } ] } },
  "size": 24,
  "aggs": { "categories": { "terms": { "field": "category" } },
            "price": { "range": { "field": "price", "ranges": [ {"to": 500}, {"from": 500, "to": 2000}, {"from": 2000} ] } } } }
"bool": { "must": [...] }Conditions that must match and that change the score.
"multi_match", "fields": ["name^3", "description"]Search two fields. ^3 makes a match in the name three times more important than a match in the description.
"filter": [ { "term": { "category": ... } } ]A filter must match, but it does not change the score. OpenSearch can cache filters, so they are cheap.
"size": 24Return the 24 best hits.
"aggs": "categories": termsCount the matching documents for each value of the keyword field category.
"aggs": "price": rangeCount the matching documents in three price ranges.
{% endcall %}

07Geographic search

A field of type {{ k.term("geo_point") }} stores a latitude and a longitude. A geo_distance query keeps the documents inside a circle, and a sort puts the nearest first. The store coordinates below are examples near the real stores of TDS Academy Market.

{% call k.sql("Q4", "Stores within 25 km, nearest first") %} 
GET stores/_search
{ "query": { "geo_distance": { "distance": "25km", "location": { "lat": 41.0082, "lon": 28.9784 } } },
  "sort":  [ { "_geo_distance": { "location": { "lat": 41.0082, "lon": 28.9784 }, "order": "asc", "unit": "km" } } ] }
"geo_distance": { "distance": "25km", ... }Keep the stores whose location is at most 25 km from the point.
"sort": "_geo_distance", "order": "asc"Sort the stores by distance, nearest first. The sort value of each hit is the distance in km.

Amazon OpenSearch Service: the AWS service

Shards and replicas, and what AWS runs for you.

08Shards, replicas and the managed service

An index is split into {{ k.term("shard") }}s. Each shard is a complete small index with a part of the documents. Shards let an index grow beyond one node and let several nodes search in parallel. Each primary shard can have {{ k.term("replica") }} shards on other nodes. A replica gives a copy for failures and more capacity for searches.

{{ k.fig("opensearch-index-shards.png", "an index split into two shards. Each shard holds a part of the documents.") }} {{ k.fig("opensearch-replicas.png", "two nodes. Each primary shard has a replica shard on the other node, so the loss of one node loses no data.") }}

When you run OpenSearch yourself, you install the nodes, set the heap memory, plan the shards, replace failed nodes, take snapshots and upgrade the version. Amazon OpenSearch Service does these tasks. You select the instance types, the number of nodes and the storage. You can place the domain in a VPC and spread it over Availability Zones.

TaskYour own OpenSearch clusterAmazon OpenSearch Service
NodesYou install, configure and replace them.AWS runs and replaces them. You select the type and the number.
SnapshotsYou configure a repository and a schedule.Automated snapshots.
UpgradesYou plan rolling upgrades.Managed version upgrades.
AccessYou add a security plugin.IAM (SigV4), VPC placement, fine-grained access control.
DashboardsYou install OpenSearch Dashboards.Included.

09OpenSearch in TDS Academy Market

  • One OpenSearch Service domain inside the VPC, with two indexes: products (200 documents, tr_folded and standard analyzers) and stores (geo_point).
  • The OpenSearch Engine App signs each request with its IAM role (SigV4). There is no password.
  • The live index products has 5 primary shards and 1 replica of each.
  • The search page has the fuzziness and analyzer experiments, and the store finder has the radius experiment.
