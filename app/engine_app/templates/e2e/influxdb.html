01The architect's view: where Timestream for InfluxDB fits

Read this section first. It gives the decision. The sections after it teach how a time-series database works.

In short: Amazon Timestream for InfluxDB runs the open-source InfluxDB for you. A time-series database stores measurements with a timestamp. Examples are a temperature every 5 minutes, the number of orders every minute, the CPU load every 10 seconds. It writes a continuous stream of small points. It answers questions about time windows, for example "the mean per 15 minutes for the last 6 hours". It also deletes old data automatically.

The key idea is the {{ k.term("series") }}: all points of one thing that you measure, in time order. A query reads a few series over a time range, and it seldom changes old points.

The questions that an architect asks, in this order

  1. Is the time the main axis of every question? If most queries start with "in the last hour", a time-series database helps.
  2. What do you measure, and which labels describe it? The labels become tags. Count their possible values first.
  3. How long is raw data useful? That is the retention period. Long-term trends can use downsampled data in a second bucket.
  4. How many points per second? It decides the instance size.
  5. InfluxDB 2 or InfluxDB 3? New workloads can use InfluxDB 3. Existing databases and Flux queries use InfluxDB 2.
  6. Must it survive the loss of an Availability Zone? Then use a Multi-AZ deployment.

Part 1

InfluxDB: points, series and Flux

Line protocol, series and cardinality, time windows and retention.

02Why a time-series database? The electricity meter

A business database keeps the current state: the stock of a product, the status of an order. When the state changes, it updates the row. A time-series database keeps every measurement and never updates it. The question is not "what is the value?" but "how did the value change?".

{% call k.callout("analogy", "Analogy") %}

The electricity meter of a house shows one number. The bill of the electricity company shows a table: the consumption of each 15 minutes for the whole month. The meter is a business database. The table on the bill is a time series. Nobody changes a line of the bill later. New lines come at the end, and after some years the old bills go away.

{% endcall %}

03Points, tags, fields and series

InfluxDB writes data in {{ k.term("line protocol") }}: one line of text for each {{ k.term("point") }}. This is the format (from the InfluxDB line protocol reference):

{% call k.sql("W1", "One point of a warehouse sensor") %} 
warehouse_env,warehouse=IST-1,sensor=temperature value=21.2 1793433600
warehouse_envThe measurement: the name of the kind of data, like the name of a table.
,warehouse=IST-1,sensor=temperatureThe tag set: key-value pairs that describe the point. InfluxDB indexes tags, so filters on tags are fast. Tag values are always text.
value=21.2The field set: the measured values. Fields are not indexed. A point must have at least one field. An integer field ends with i, for example count=14i.
1793433600The timestamp, here in seconds since 1 January 1970 (UTC). The write request says the precision. Lale Market writes with precision s.
{% endcall %}

A {{ k.term("series") }} is the group of points with the same measurement, the same tag set and the same field key. InfluxDB stores the points of one series together, sorted by time. The number of different series is the {{ k.term("cardinality") }}. These six lines are the input of the simulation:

{{ k.sample("ix_lines", "six points in line protocol") }} {% call k.predict("How many different series do the six lines make?") %}

Four: IST-1 temperature (two points), IST-1 humidity, ANK-1 temperature and orders with channel=web (two points).

{% endcall %} {{ k.sim("series", "From lines to series") }}

Identifiers: a point has no id of its own. The series key and the timestamp identify it. If you write a second point with the same series key and the same timestamp, InfluxDB does not add a point. The new field value replaces the old one. The warehouse codes IST-1 and ANK-1 belong to the warehouse list of Lale Market. The tags borrow these codes, so a chart can show the name of the warehouse.

{{ k.quiz("ix-q1", "Which part of a point is not indexed?", ["The measurement", "The tags", "The fields", "The tag keys"], 2, "Fields hold the measured values and are not indexed. A filter on a field value must read the points.") }}

04Flux: a query is a pipeline

InfluxDB 2 uses the query language {{ k.term("Flux") }}. A Flux query is a chain of functions. The operator |> sends the output of one function into the next one, like a pipe in a shell. This is the real query of the Lale Market operations page (from engines/influxdb.py):

{% call k.sql("Q1", "Mean temperature per 15 minutes, last 6 hours") %} 
from(bucket: "metrics")
  |> range(start: -6h)
  |> filter(fn: (r) => r._measurement == "warehouse_env" and r.sensor == "temperature")
  |> aggregateWindow(every: 15m, fn: mean, createEmpty: false)
from(bucket: "metrics")Read from the bucket metrics. A bucket is a named store with its own retention period.
|> range(start: -6h)Keep only the points of the last 6 hours. Every Flux query on a bucket needs a range, because InfluxDB finds data by time first.
|> filter(fn: (r) => ...)Keep only the rows r of the measurement warehouse_env with the tag sensor = temperature. The result has one series for each warehouse.
|> aggregateWindow(every: 15m, fn: mean, ...)Cut each series into windows of 15 minutes and calculate the mean of each window.
createEmpty: falseDo not return a row for a window that has no points.
{% endcall %}

The column _value holds the field value, and the column _time holds the timestamp. The tags become columns too, for example warehouse.

06Retention: old data goes away by itself

Each bucket has a {{ k.term("retention period") }}. InfluxDB stores the points of a time span together in a shard group. When all points of a shard group are older than the retention period, InfluxDB drops the complete shard group (InfluxDB data retention). It is cheap, because it deletes whole files and not single points.

{{ k.sim("retention", "A bucket with a retention period of 3 days") }}

For long-term trends, a common pattern uses two buckets. A task reads the raw bucket every hour, calculates hourly means with aggregateWindow and writes them into a second bucket with a long retention period.

Amazon Timestream for InfluxDB: the AWS service

Managed InfluxDB instances and clusters, in your VPC.

07What AWS runs for you

AWS describes the service as follows: Timestream for InfluxDB runs InfluxDB 3 Core and Enterprise for new workloads and InfluxDB 2 for existing databases. It does the provisioning, the patching, the backups and the failover (Amazon Timestream for InfluxDB). An InfluxDB 2 deployment can be Multi-AZ. Then it replicates the data synchronously to a standby in a second Availability Zone, and it fails over automatically (AWS News Blog). Your applications keep the open-source APIs, the client libraries and the Telegraf plugins.

TaskYour own InfluxDBTimestream for InfluxDB
ServersYou install, patch and size them.AWS provisions and patches. You select the instance class and the storage.
AvailabilityYou build replication and failover.Multi-AZ standby (InfluxDB 2) or a multi-node cluster (InfluxDB 3 Enterprise).
BackupsYou schedule and test them.Managed backups.
Network and secretsYou configure TLS and passwords.Runs in your VPC. Credentials in AWS Secrets Manager. Encryption at rest and in transit.
APIs and toolsOpen-source InfluxDB.The same open-source APIs, clients and Telegraf.

08Timestream for InfluxDB in Lale Market

  • One InfluxDB 2 instance in the data subnets. The InfluxDB Engine App connects on HTTPS port 8086 with a user name and a password from Secrets Manager.
  • The organization is dbws and the bucket is metrics.
  • The Seed deletes the measurements warehouse_env and orders, and writes the sensor points and the orders-per-minute points again.
  • The admin page "Operations" runs Q1 with a window of 1, 5 or 15 minutes or 1 hour, over 1, 6 or 24 hours.
  • A checkout writes orders,channel=workshop count=1i. The reset deletes only the points with channel=workshop.
