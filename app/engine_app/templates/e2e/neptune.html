01The architect's view: where Neptune fits

Read this section first. It gives the decision. The sections after it teach how a graph works.

In short: Amazon Neptune is a managed graph database. It stores things (vertices) and the relations between them (edges) as data of the same importance. It answers questions that follow relations: "who bought what", "who knows whom", "how are these two accounts connected". Select it when the relations are the question, and when the number of hops is large or unknown.

The key idea is the {{ k.term("traversal") }}: a query starts at one vertex and walks along its edges. It reads only the part of the graph that it walks through.

The questions that an architect asks, in this order

  1. Are the relations the question? If the answer reads "follow X to Y to Z", a graph helps. If it reads "sum all X", it does not.
  2. How many hops, and is the number known? One known join is easy in SQL. Three or more, or "any number", points to a graph.
  3. Property graph or RDF? Application data with properties usually uses a property graph (openCypher, Gremlin). Shared vocabularies use RDF (SPARQL).
  4. Where is the source of truth? A recommendation graph is often a copy of the order database. A fraud graph can be the source.
  5. Per-request queries or whole-graph algorithms? Per-request queries use Neptune Database. Algorithms over the whole graph (PageRank, communities) fit Neptune Analytics.
  6. How steady is the traffic? Steady traffic uses provisioned instances. Variable traffic can use Neptune Serverless.

Where Neptune sits in Lale Market

The orders live in the order database. The Seed copies each customer and each product into Neptune as a vertex. It also copies each order line as a BOUGHT edge from the customer to the product. The product page reads "bought together" products from Neptune. The admin page "Customer graph" draws the neighbours of one customer. When a visitor buys a product in the shop, the Neptune Engine App adds new BOUGHT edges at once. The next recommendation already includes them.

Part 1

The property graph and openCypher

Vertices, edges, patterns, hops and paths.

02Why a graph? The subway map

A table stores things in rows. A relation between two rows is a value in a column: the order line has a customer_id and a product_id. To follow a relation, the database looks up the value in an index and joins the two rows. One join is cheap. Questions like "customers like me" need three joins of the same large table, and "connected in any number of steps" needs a recursive query.

{% call k.callout("analogy", "Analogy") %}

A subway map shows stations as points and the lines between them. To go from one station to another, you do not read the list of all stations. You put your finger on your station and follow the lines. A graph database stores data like this map. The relations are lines that a query can follow, not values that it must look up.

{% endcall %}

03The property graph: vertices, edges, labels and properties

A {{ k.term("property graph") }} has two kinds of elements:

  • A {{ k.term("vertex") }} (also "node") is a thing: a customer, a product. It has a label, for example Customer, and properties, for example name.
  • An {{ k.term("edge") }} is a relation between two vertices. It has a direction, a label, for example BOUGHT, and properties, for example order_id and qty.
{{ k.fig("neptune-property-graph.png", "a labeled property graph. Person vertices have WROTE and PURCHASED edges to Book vertices. Each edge has a date property.") }}

This is the teaching graph of this page. The four customers and five products are real records of Lale Market. The ten BOUGHT edges are examples.

{{ k.sample("g_customers", "Customer vertices", key=["~id"]) }} {{ k.sample("g_products", "Product vertices", key=["~id"]) }} {{ k.sample("g_bought", "BOUGHT edges", key=["~id"], ref=["~from", "~to"]) }}

Identifiers: each vertex and each edge has its own ~id. The customer table of the shop owns the customer id, and the catalog owns the product id. The Seed borrows these ids as the ~id of the vertices. An edge does not copy the customer. It stores the ~id of its start vertex in ~from and the ~id of its end vertex in ~to. The edge e1 belongs to the customer C00001 and points to the product P0001. The column names ~id, ~from, ~to and ~label are the names that the Neptune bulk loader uses in CSV files.

04openCypher patterns: two hops from a product

openCypher draws the pattern that it looks for with brackets and arrows: (a)-[:BOUGHT]->(b) means "a vertex a with a BOUGHT edge to a vertex b". This is the real query of the product page (from engines/neptune.py):

{% call k.sql("Q1", "Customers who bought this also bought") %} 
MATCH (p:Product {`~id`: $pid})<-[:BOUGHT]-(c:Customer)-[:BOUGHT]->(rec:Product)
WHERE rec <> p
RETURN rec.`~id` AS product_id, rec.name AS name, rec.category AS category, count(DISTINCT c) AS score
ORDER BY score DESC, product_id LIMIT 6
MATCH (p:Product {`~id`: $pid})Start at one Product vertex. $pid is a parameter, for example P0001. The id lookup uses an index, so it reads one vertex.
<-[:BOUGHT]-(c:Customer)Hop 1. Follow the BOUGHT edges that come into the product. Each one leads to a customer c who bought it.
-[:BOUGHT]->(rec:Product)Hop 2. From each of these customers, follow the BOUGHT edges that go out. Each one leads to a product rec.
WHERE rec <> pDo not recommend the start product.
count(DISTINCT c) AS scoreFor each product rec, count the different customers who reach it. More shared buyers give a higher score.
ORDER BY score DESC, product_id LIMIT 6Return the six best products. For equal scores, the product id sets the order.
{% endcall %} {% call k.predict("Use the edge table. Which products does Q1 return for P0001, and with which scores?") %}

The buyers of P0001 are C00001, C00002 and C00003. Their other products are P0016 (C00001 and C00002), P0175 (C00002 and C00003) and P0044 (C00003). So P0016 and P0175 get score 2, and P0044 gets score 1.

{% endcall %} {{ k.sim("hop2", "Two hops from P0001") }}

Look at the counter "edges read". The traversal reads the edges near its start vertex. It does not read the edges of Zeynep Şahin, because no path from P0001 reaches her. This is why a graph query stays fast when the graph grows. Its cost depends on the neighbours that it visits, not on the total number of vertices.

05Three hops: a personal recommendation

The product page works for every visitor. A personal recommendation starts at the customer instead and goes one hop further: my products, other buyers of my products, and their other products.

{% call k.sql("Q2", "Products that customers like me bought") %} 
MATCH (me:Customer {`~id`: $cid})-[:BOUGHT]->(:Product)<-[:BOUGHT]-(o:Customer)-[:BOUGHT]->(rec:Product)
WHERE o <> me AND NOT (me)-[:BOUGHT]->(rec)
RETURN rec.`~id` AS product_id, rec.name AS name, rec.category AS category, count(DISTINCT o) AS score
ORDER BY score DESC, product_id LIMIT 6
(me:Customer {`~id`: $cid})-[:BOUGHT]->(:Product)Hop 1. The products that I bought. The product vertex has no name in the query, because the query does not return it.
<-[:BOUGHT]-(o:Customer)Hop 2. Other customers o who bought the same products.
-[:BOUGHT]->(rec:Product)Hop 3. The products that these customers bought.
WHERE o <> meI am not a "customer like me".
AND NOT (me)-[:BOUGHT]->(rec)Do not recommend a product that I bought already. This is a pattern used as a condition.
count(DISTINCT o) AS scoreThe number of similar customers who bought the product.

06Paths of any length

Some questions do not know the number of hops. "Is this account connected to a fraud account?" can need two hops or six. openCypher writes a variable length with a star:

{% call k.sql("Q3", "The shortest connection between two customers") %} 
MATCH path = shortestPath((a:Customer {`~id`: 'C00005'})-[:BOUGHT*..6]-(b:Customer {`~id`: 'C00001'}))
RETURN [n IN nodes(path) | n.`~id`] AS ids, length(path) AS hops
-[:BOUGHT*..6]-Follow from 1 to 6 BOUGHT edges. There is no arrow head, so the query follows the edges in both directions.
shortestPath(...)Return the path with the smallest number of hops.
nodes(path), length(path)The vertices on the path, and the number of edges.
{% endcall %}

The simulation shows the idea behind a shortest path: a breadth-first search. It visits all vertices at distance 1, then all at distance 2, and it stops at the level where it finds the target.

{{ k.sim("path", "From Zeynep Şahin to Ayşe Yılmaz") }}

The same query in Gremlin, the other property-graph language of Neptune, is a chain of steps. Neptune runs Gremlin and openCypher on the same property-graph data (Accessing graph data in Neptune):

{% call k.sql("Q4", "Q1 in Gremlin") %} 
g.V('P0001').as('p').in('BOUGHT').out('BOUGHT').
  where(neq('p')).groupCount().by(id).
  order(local).by(values, desc).limit(local, 6)
g.V('P0001').as('p')Start at the vertex with the id P0001, and give it the step label p.
.in('BOUGHT').out('BOUGHT')Hop 1 against the edge direction, then hop 2 with the edge direction.
.where(neq('p'))Drop the vertex that is equal to the step label p, the start product.
.groupCount().by(id)Count how often each product appears. This counts paths, not different customers. If one customer bought a product twice, Q1 counts the customer once, but this query counts two paths.
.order(local)...limit(local, 6)Sort the counts, highest first, and keep six.
{% endcall %}

07The same question in SQL

A relational database can answer Q1 with a self-join of the order lines. Each hop is one more copy of the table in the FROM clause:

{% call k.sql("Q5", "Q1 in SQL") %} 
SELECT b.product_id, count(DISTINCT b.customer_id) AS score
FROM   bought a
JOIN   bought b ON b.customer_id = a.customer_id
WHERE  a.product_id = 'P0001' AND b.product_id <> 'P0001'
GROUP  BY b.product_id
ORDER  BY score DESC, b.product_id LIMIT 6;
FROM bought a ... WHERE a.product_id = 'P0001'Hop 1: the rows of the buyers of P0001.
JOIN bought b ON b.customer_id = a.customer_idHop 2: all rows of these buyers. This is a self-join, a join of a table with itself.
GROUP BY ... count(DISTINCT ...)The score, as in Q1.
{% endcall %}

For two hops, this SQL is fine, and with the right indexes it is fast. The difference grows with the depth. Three hops need a third copy of the table, and "any number of hops" needs WITH RECURSIVE. Each extra hop multiplies the rows in the middle of the plan. A graph database stores the edges so that the next hop starts directly from the vertex that the last hop reached.

Amazon Neptune: the AWS service

A cluster, a shared storage volume, and three query languages.

08The Neptune cluster and what AWS runs

A Neptune DB cluster has one primary instance and up to 15 read replicas (Neptune reliability pillar). The primary instance reads and writes. The replicas only read. All instances use the same cluster volume. Neptune keeps copies of the data across three Availability Zones, and the amount of replication does not depend on the number of instances (Neptune storage). Because a new replica connects to the volume that already exists, Neptune does not copy the graph to add it.

When the primary instance fails, Neptune promotes a replica. The guide says that the interruption is "generally less than 30 seconds".

One cluster can store property-graph data and RDF data. Neptune has a Gremlin endpoint, an openCypher endpoint and a SPARQL endpoint. Gremlin and openCypher read the same property-graph data. SPARQL reads only RDF data (Neptune FAQs).

09Neptune in Lale Market

  • One Neptune cluster in the data subnets. The Neptune Engine App connects to the cluster endpoint on HTTPS port 8182.
  • The Engine App signs each request with its IAM role (SigV4, service name neptune-db). There is no password.
  • The Seed deletes the graph, creates the Customer and Product vertices, and creates one BOUGHT edge for each order line that is not cancelled. It sends the edges in groups of 500 with UNWIND.
  • The product page runs Q1. The persona recommendations run Q2. The admin page "Customer graph" draws the neighbours of one customer.
  • A purchase in the shop creates new BOUGHT edges with an order id that starts with W. The reset deletes only these edges.
