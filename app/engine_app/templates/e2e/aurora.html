00What you will learn

Lale Market keeps its orders in Amazon Aurora PostgreSQL. Each order changes the stock, writes an order header and writes order lines. These writes must happen together, or not at all. Many shoppers do this at the same time.

After this tutorial, you can do these tasks:

  1. Draw the four Lale Market tables and the keys that connect them.
  2. Read a JOIN and say which rows each step of the Engine touches.
  3. Read a query plan and tell an index scan from a full table scan.
  4. Explain how a transaction and a row lock stop the shop from selling the last piece two times.
  5. Say when Aurora is the correct Engine, and when a different Engine is better.

01The model: tables with a set shape

A {{ k.term("relational database") }} keeps data in tables. A table has columns, and each column has one data type. Each row of the table has a value for each column. The list of tables, columns, types and rules is the {{ k.term("schema") }}. You define the schema before you write the first row.

This is the real customers table of Lale Market, with three of its 1,000 rows:

customers (customer_id text PRIMARY KEY, name text NOT NULL, email text, city text, segment text, created_at timestamptz)

C00003Elif Kayaelif.kaya@example.comİzmirbireysel
{% call k.callout("analogy", "Analogy") %}

A table is like a printed form with set boxes. Each customer fills the same boxes. You cannot write a phone number in the box for the city, because the database checks the type of each value. A new kind of information needs a new box for all forms: ALTER TABLE ... ADD COLUMN.

{% endcall %}

On disk, PostgreSQL stores each table and each index as a list of pages of one size, usually 8 kB (PostgreSQL: Database Page Layout). A page holds many rows. To read one row, the Engine reads the full page that holds it. Keep this picture in mind: the cost of a query is mostly the number of pages that it reads.

{% call k.query("aurora", "A1", "How many rows are in each table?") %} 
SELECT 'customers' AS table_name, count(*) AS rows FROM customers
UNION ALL SELECT 'products', count(*) FROM products
UNION ALL SELECT 'orders', count(*) FROM orders
UNION ALL SELECT 'order_items', count(*) FROM order_items;

Purpose: see the size of the data before you query it. count(*) counts rows. UNION ALL puts the four results under each other.

{% endcall %} {% call k.query("aurora", "A2", "Read one customer by the primary key") %} 
SELECT * FROM customers WHERE customer_id = 'C00001';

Purpose: get exactly one row. The {{ k.term("primary key") }} customer_id is unique, so the result has zero or one row.

{% endcall %}

02Keys: how four tables make one order

An order has a header (who, when, status, total) and one or more lines (which product, how many, at which price). Lale Market puts these facts in four tables. Keys connect the tables:

  • A primary key (PK) is the column or columns that identify one row. No two rows can have the same primary key.
  • A {{ k.term("foreign key") }} (FK) is a column that holds the primary key of a row in a different table. PostgreSQL rejects a foreign key value that points to no row.
{{ k.fig("aurora-er-diagram.png", "each box is a table. PK marks the primary key and FK marks a foreign key. Each line connects a foreign key to the primary key that it points to. The Lale Market tables use the same idea with four tables.") }}

The total is the sum of the lines: 2,651.39 + 2,721.65 + 3 × 2,693.65 + 2 × 767.49 = 14,988.97.

Why not one wide table with the customer name and the product name in each line? Because then one fact has many copies. If Ayşe changes her e-mail address, you must change each line of each order that she ever placed. If one change fails, the copies disagree. With separate tables, each fact has one place. This design rule is {{ k.term("normalization") }}.

One copy is on purpose: order_items.unit_price. The price in products can change tomorrow. The order must keep the price that the customer paid. So the order line stores the price at the time of the order.

{% call k.predict("The products table gets a new price for P0142 tomorrow. Does the total of order O000001 change?") %}

No. The order line has its own unit_price (2,693.65), and the order row keeps its own orders.total. Only new orders use the new price. This copy is a business decision, not an accident.

03JOIN: put the pieces together again

Storage is split. The shop page needs one picture. A {{ k.term("JOIN") }} combines rows of two tables where a condition is true, usually "the foreign key equals the primary key".

{% call k.predict("Order O000001 has 4 lines. How many rows does a JOIN of orders, customers, order_items and products return for this order?") %}

4 rows. Each order line matches one order, one customer and one product. The order and customer columns repeat in each of the 4 result rows. The result repeats data, but the storage does not.

{% endcall %} {% call k.query("aurora", "A3", "Order O000001 as one result") %} 
SELECT o.order_id, o.order_date::date AS order_date, c.name AS customer,
       p.name AS product, oi.qty, oi.unit_price, oi.qty * oi.unit_price AS line_total
FROM orders o
JOIN customers   c  ON c.customer_id = o.customer_id
JOIN order_items oi ON oi.order_id   = o.order_id
JOIN products    p  ON p.product_id  = oi.product_id
WHERE o.order_id = 'O000001';

Purpose: show one order with the customer name and the product names. How the Engine can run it:

  1. Find the row O000001 in orders with the primary key index. This reads a few pages, not the full table.
  2. Use o.customer_id (C00001) to find one row in customers, again by its primary key index.
  3. Find the lines of O000001 in order_items. The primary key (order_id, product_id) starts with order_id, so its index finds them.
  4. For each of the 4 lines, find the product by product_id. The result is 4 rows.

The planner of PostgreSQL selects the order of these steps and the join method. The steps above show one correct plan, not the only plan.

{% endcall %} {{ k.quiz("aurora-q2", "Why is a JOIN on primary keys fast, also when the tables are large?", ["The Engine copies the tables to memory first", "Each lookup uses an index and reads few pages", "The Engine stores the joined result on disk", "PostgreSQL caches every possible join in advance"], 1, "The primary key has a B-tree index. Each lookup reads a few pages, and this number grows very slowly with the table size.") }}

04Aggregation: many rows become one number

A shop manager asks: "Which category earns the most?" The answer needs all order lines, grouped by the category of the product.

{% call k.query("aurora", "A4", "Revenue per category") %} 
SELECT p.category, count(DISTINCT o.order_id) AS orders,
       sum(oi.qty) AS pieces, round(sum(oi.qty * oi.unit_price), 2) AS revenue
FROM order_items oi
JOIN orders o   ON o.order_id = oi.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status <> 'cancelled'
GROUP BY p.category
ORDER BY revenue DESC;
  1. Read all order lines (about 12,500 rows), because the question is about all of them.
  2. Join each line to its order, and drop the lines of cancelled orders.
  3. Join each line to its product to get the category.
  4. Put the lines into five groups, one for each category. Sum and count inside each group.
  5. Sort the five result rows by revenue.
{% endcall %}

This query reads the full tables. On Lale Market data, this takes milliseconds. On years of orders, it can take minutes, and it competes with the checkout for the same Engine. The Redshift tutorial shows an Engine that AWS built for this kind of query.

05Indexes and query plans

An {{ k.term("index") }} is a second structure next to the table. It keeps the values of one or more columns in sorted order, and each entry points to the row. The default index type of PostgreSQL is the {{ k.term("B-tree") }} (PostgreSQL: Index Types). A primary key automatically gets a unique B-tree index (PostgreSQL: Constraints).

{{ k.fig("aurora-btree.png", "the root node holds 7 and 16. To find 12, the Engine goes to the middle child, because 7 < 12 < 16. A search reads one node on each level. A tree of millions of keys has only a few levels.") }} {% call k.callout("analogy", "Analogy") %}

An index is like the index at the back of a book. To find "transaction", you do not read all pages. You look in the sorted index, and it gives the page number. The book is the table. The page number is the pointer to the row.

{% endcall %} {% call k.query("aurora", "A5", "Which indexes exist?") %} 
SELECT tablename, indexname, indexdef
FROM pg_indexes WHERE schemaname = 'public' ORDER BY tablename, indexname;

Purpose: list each index. You see the primary key indexes (..._pkey) and the two extra indexes on orders.customer_id and orders.visitor_id. The email column of customers has no index.

{% endcall %} {% call k.predict("You look up a customer by customer_id, then by email. Which of the two queries reads more pages?") %}

The query by email. customer_id has an index, so PostgreSQL goes straight to one row (Index Scan). email has no index, so PostgreSQL reads each row of the table and tests the filter (Seq Scan). Run A6 and A7 and compare the "Buffers" lines.

{% endcall %} {% call k.query("aurora", "A6", "Plan of a lookup by primary key") %} 
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM customers WHERE customer_id = 'C00450';

EXPLAIN ANALYZE runs the query and shows the plan with the real time of each step (PostgreSQL: Using EXPLAIN). BUFFERS adds the number of pages that the step read.

{% endcall %} {% call k.query("aurora", "A7", "Plan of a filter on a column with no index") %} 
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM customers WHERE email = 'ayse.yilmaz@example.com';

Look for Seq Scan and Rows Removed by Filter. The Engine read 1,000 rows to return 1 row.

{% endcall %}

An index is not free. Each INSERT and each UPDATE of an indexed column also changes the index. So add an index for the queries that the shop runs often, not for each column.

{{ k.quiz("aurora-q3", "The plan of a query shows Seq Scan on orders and Rows Removed by Filter: 4,999. Which change helps most?", ["Add more Aurora Replicas to the cluster", "Add an index on the filtered column", "Change the column type to text", "Run the query two times in a row"], 1, "A Seq Scan with many removed rows means that no index helps the filter. An index on the filtered column lets the Engine go straight to the matching rows.") }}

06Constraints: the database refuses bad data

The application can have bugs. A {{ k.term("constraint") }} is a rule in the schema, so PostgreSQL checks it for each write from each application. Lale Market uses three kinds: PRIMARY KEY, FOREIGN KEY (REFERENCES) and CHECK (stock >= 0). The next two queries try to break a rule. They run inside a transaction that ends with ROLLBACK, so no change stays.

{% call k.query("aurora", "A8", "Write an order line for a product that does not exist") %} 
BEGIN;
INSERT INTO order_items VALUES ('O000001', 'P9999', 1, 10.00);   -- P9999 is not in products
ROLLBACK;

Expected: PostgreSQL refuses with a foreign key violation.

{% endcall %} {% call k.query("aurora", "A9", "Make the stock negative") %} 
BEGIN;
UPDATE products SET stock = stock - 100000 WHERE product_id = 'P0001';
ROLLBACK;

Expected: PostgreSQL refuses with a check constraint violation.

{% endcall %}

07Transactions: all or nothing, one at a time

A {{ k.term("transaction") }} groups statements into one unit. PostgreSQL makes all of its changes visible at COMMIT, or none of them at ROLLBACK (PostgreSQL: Transactions). These are the real statements of the Lale Market checkout (from engines/aurora.py):

BEGIN;
UPDATE products SET stock = stock - 2 WHERE product_id = 'P0001' AND stock >= 2;  -- one per cart line
INSERT INTO orders VALUES ('W1793...', 'C00001', '<visitor>', now(), 'processing', 6747.68);
INSERT INTO order_items VALUES ('W1793...', 'P0001', 2, 3373.84);
COMMIT;

If the payment fails after the stock UPDATE, the app sends ROLLBACK. The stock comes back, and no order row exists. This is atomicity, the "A" of {{ k.term("ACID") }}.

The last piece: two checkouts at the same time

Product P0001 has stock 1. Ayşe and Mert click "Place the order" in the same second. Look at what a naive program does, step by step:

TimeAyşe (naive program)Mert (naive program)stock in the table
t1SELECT stock → 11
t2SELECT stock → 11
t31 ≥ 1, so UPDATE ... SET stock = 00
t41 ≥ 1, so UPDATE ... SET stock = 00 (two pieces sold)

Both programs read 1 before a write. The shop sold one piece two times. This is a {{ k.term("lost update") }}.

Lale Market puts the test inside the UPDATE: SET stock = stock - 1 WHERE ... AND stock >= 1. An UPDATE takes a row lock. Mert's UPDATE waits until Ayşe's transaction ends. Then it reads the new value (0), the condition is false, and it changes 0 rows. The app sees "0 rows" and tells Mert that the stock is not enough.

{% call k.query("aurora", "A10", "The conditional UPDATE of the checkout") %} 
BEGIN;
UPDATE products SET stock = stock - 1
WHERE product_id = 'P0001' AND stock >= 1
RETURNING product_id, stock AS stock_after;
ROLLBACK;

Purpose: see the test and the change in one statement. RETURNING shows the new value. The ROLLBACK gives the piece back.

{% endcall %} {% call k.callout("analogy", "Analogy") %}

A row lock is like the key of a single toilet in a café. The person with the key goes in. The next person waits at the door. When the key comes back, the next person goes in and sees the room as it is now, not as it was before the wait.

{% endcall %}

Readers do not wait for writers. PostgreSQL uses {{ k.term("MVCC") }}: each statement sees a snapshot of committed data. So a SELECT does not block an UPDATE, and an UPDATE does not block a SELECT (PostgreSQL: MVCC Introduction).

{{ k.quiz("aurora-q4", "Why does the checkout put AND stock >= 1 inside the UPDATE instead of a SELECT before it?", ["It makes the SQL text shorter to read", "The test and the change happen under one row lock", "SELECT statements are not allowed in a transaction", "It lets the UPDATE skip the primary key index"], 1, "Between a SELECT and a later UPDATE, another transaction can change the row. A single UPDATE tests and changes the row while it holds the row lock.") }}

08What Aurora adds to PostgreSQL

The SQL in this tutorial is PostgreSQL. Aurora PostgreSQL runs the PostgreSQL engine, but it changes the storage layer. An Aurora {{ k.term("DB cluster") }} has DB instances and one cluster volume. The primary (writer) instance does all the writes. Up to 15 Aurora Replicas connect to the same volume and serve reads. The cluster volume has copies of the data in three Availability Zones (Aurora DB clusters, Aurora storage).

{{ k.fig("aurora-cluster.png", "the writer and the two readers sit in three Availability Zones, but all three use one shared storage volume. A new reader needs no copy of the data. The volume also sends continuous backups to Amazon S3.") }}

In Lale Market, the Engine App connects to the writer endpoint, because the checkout writes. A report that only reads could use the reader endpoint.
