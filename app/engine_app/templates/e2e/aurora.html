00What you will learn, and how to use this page

This tutorial has two parts. Part 1 teaches PostgreSQL itself. You learn how it stores data and how it answers a question. You also learn how it keeps data correct when many people write at the same time. Everything in Part 1 is true for any PostgreSQL server, on your laptop or in a data center. Part 2 shows what Amazon Aurora PostgreSQL changes. Aurora runs the same PostgreSQL, but it replaces the storage and the operations around it.

The examples come from Lale Market, the shop of this workshop. Lale Market keeps its orders in Aurora PostgreSQL. When a different example makes an idea easier to see, the tutorial uses that example instead: a library, a bank account, a café.

After this tutorial, you can do these tasks:

  1. Read a CREATE TABLE statement and say what each line allows and refuses.
  2. Say which table owns which identifier, and which tables borrow it.
  3. Read a SELECT with JOIN and GROUP BY, clause by clause, and predict its result from the input tables.
  4. Explain why an index makes one query fast and each write a little slower.
  5. Explain how a transaction and a row lock stop a shop from selling the last piece two times.
  6. Explain what Aurora adds to PostgreSQL, and when a different AWS database is a better choice.

Four kinds of boxes help you:

  • Simulation: press Play or Next step. The input tables change color while PostgreSQL works, and the result table fills row by row.
  • Predict first: write your answer before you open the solution. A wrong guess that you correct teaches more than a right answer that you read.
  • Checkpoint: a question with one correct answer. The score at the left counts your first answers.
  • Analogy: a picture from daily life. An analogy helps you remember, but the text before it is the exact rule.
Part 1

PostgreSQL: the database engine

What a relational database is, and how PostgreSQL answers questions and protects data.

01Why not a spreadsheet? The problem that a database solves

Think about a small bookshop with three cashiers. The owner keeps the stock in one spreadsheet file on a shared disk. For one person, this works well. Then the shop gets busy, and four problems appear.

  1. Two people change the same cell. Cashier A opens the file and sees 1 copy of a book. Cashier B opens the same file and also sees 1 copy. Both sell the book, and both save. The file now says 0, but the shop sold 2 copies of a book that it had 1 time.
  2. The computer stops in the middle of a change. A sale has two parts: lower the stock, and write the sale into the sales sheet. The power goes off after the first part. Now the stock is lower, but no sale exists.
  3. Wrong data gets in. Somebody types "ten" into a price cell, or a negative stock. The spreadsheet accepts it, and every total after it is wrong.
  4. Questions get slow. "Which books did customer 4021 buy last year?" With 2 million rows, somebody must filter by hand, or the program must read the full file.

A database server solves these four problems in one program. It accepts many connections at the same time, and it puts their changes in a safe order. It writes each change to a log on disk before it reports success. So a power failure does not lose a change that it reported as done. It tests the rules that you declare, and it refuses data that breaks them. It keeps extra structures (indexes) that answer frequent questions without a full read.

PostgreSQL is one such server. It is open source, and it is one of the most used relational databases. Your application does not open a file. It connects to the PostgreSQL server over the network (TCP port 5432 by default) and sends text commands in SQL, the Structured Query Language. The server does the work and sends back rows. In Lale Market, the application is the Aurora Engine App on an EC2 instance, and it sends SQL with the Python driver psycopg.

02Table, row, column, data type, schema

A {{ k.term("relational database") }} keeps data in tables. Start with a library, because everybody knows one. A library has a list of books. Each book has a title, an author, a year and a number of copies. In a database, this list is a table named books.

  • A column is one kind of information: title, author, year, copies. Each column has a name and a data type. The data type says which values the column accepts. The column year has the type integer, so it accepts 1998 but refuses "nineteen ninety-eight".
  • A row is one book: one value for each column. A table with 40,000 books has 40,000 rows.
  • The {{ k.term("schema") }} is the description of all tables: their names, their columns, the data types and the rules. You write the schema first, with CREATE TABLE. Only then can rows go into the table.

Now the real table of Lale Market. This is the statement that creates the table of customers (from engines/aurora.py):

CREATE TABLE customers (
  customer_id text PRIMARY KEY,
  name        text NOT NULL,
  email       text,
  city        text,
  segment     text,
  created_at  timestamptz
);

Read it line by line:

CREATE TABLE customers ( ... )Make a new table with the name customers. The lines inside the parentheses are its columns, one column on each line.
customer_id text PRIMARY KEYA column with the name customer_id. Its type is text, so it holds characters such as C00001. PRIMARY KEY makes this column the identifier of the row. PostgreSQL refuses an empty value and a value that another row already has.
name text NOT NULLThe name of the customer. NOT NULL means that the value must be present. PostgreSQL refuses a row with no name.
email text, city text, segment textThree text columns with no extra rule. They can be empty. In SQL, the name of an empty value is NULL: "unknown" or "not given".
created_at timestamptzA date and a time with a time zone. PostgreSQL refuses a value that is not a valid point in time, such as "31 February".

This tutorial uses a small copy of the shop, so that you can see every row. The names and prices come from the real Lale Market data. The stock values and the orders after O000001 are examples. The real tables have 1,000 customers, 200 products, about 5,000 orders and about 12,500 order lines.

How PostgreSQL keeps a table on disk

PostgreSQL stores each table in a file. The file is a list of {{ k.term("page") }}s of the same size, usually 8 kB each (PostgreSQL: Database Page Layout). A page holds as many rows as fit into it. A customer row of about 100 bytes means about 70 rows in one page, so 1,000 customers fit in about 13 to 15 pages.

The disk and the memory always move full pages. To read one row, PostgreSQL reads the full page that holds it. So the cost of a query is mostly the number of pages that it must read. Keep this rule in mind. Every later section (indexes, joins, aggregation) comes back to it.

Your first query: SELECT, FROM, WHERE

A question to the database is a {{ k.term("query") }}. The most common query is SELECT. It has three main parts:

FROM customers
WHERE city = 'İstanbul';

SELECT customer_id, name, cityThe columns of the result. The table has six columns, but the result shows only these three. SELECT * means "all columns".

The input is the six rows of customers above. Two customers live in İstanbul: Ayşe Yılmaz and Zeynep Şahin.

03Identifiers: each table owns one, and borrows others

A shop must store facts about different things: customers, products, orders, and the lines of each order. Each kind of thing gets its own table. Each table owns an identifier. An {{ k.term("identifier") }} is a value that names exactly one row of that table, and never changes.

A table uses the identifier of a different table to say "this row is about that thing". It does not copy the other thing. It only borrows its identifier. The borrowed column is a {{ k.term("foreign key") }}. The owned column is the {{ k.term("primary key") }}.

This is the ownership in Lale Market. Read each row as a sentence.

TableThe identifier that it ownsThe identifiers that it borrows
customersThe customers table owns customer_id. Each customer has one, for example C00001 for Ayşe Yılmaz.It borrows no identifier.
productsThe products table owns product_id. Each product has one, for example P0044 for the book "Kapadokya Bulut Mimarisi 44".It borrows no identifier.
ordersThe orders table owns order_id. Each order has one, for example O000001. It borrows customer_id from the customers table. The value says which customer placed the order.
order_itemsThe order_items table owns the pair (order_id, product_id). One product can appear only one time in one order. It borrows order_id from the orders table and product_id from the products table. Together they say "this many pieces of this product, in this order".

In the tables below, a yellow column is an identifier that the table owns. A blue-green column is an identifier that the table borrows. These are the input tables for the rest of Part 1. Come back to them when a question asks about the data.

{{ k.sample("customers", "customers: owns customer_id", key=["customer_id"]) }} {{ k.sample("products", "products: owns product_id (stock values are examples)", key=["product_id"]) }} {{ k.sample("orders", "orders: owns order_id, borrows customer_id from customers", key=["order_id"], ref=["customer_id"]) }} {{ k.sample("order_items", "order_items: owns the pair (order_id, product_id), borrows order_id from orders and product_id from products", key=["order_id", "product_id"], ref=["order_id", "product_id"]) }}

Follow one order with your eyes. Order O000001 belongs to customer C00001, because the orders table says so. The customers table tells us that C00001 is Ayşe Yılmaz from İstanbul. The order_items table has four lines with order_id O000001. The third line says that Ayşe bought 3 pieces of product P0142. Each piece cost 2,693.65. The products table tells us that P0142 is "Ege Hava Temizleyici 142". The order total is the sum of its lines. 1 × 2,651.39 + 1 × 2,721.65 + 3 × 2,693.65 + 2 × 767.49 = 14,988.97.

Why the database checks borrowed identifiers

The schema of order_items says product_id text REFERENCES products. This clause tells PostgreSQL: "a value in this column must exist as an identifier in products". If a program tries to save an order line for product P9999, and no product owns P9999, PostgreSQL refuses the line. Without this rule, the shop could have order lines for products that nobody can find.

Why not one large table?

A beginner often asks: "Why four tables? One table with all the columns is simpler." Look at what one large table looks like:

order_lines_wide: one table with everything (a bad design, for comparison)
order_idcustomer_namecustomer_emailproduct_nameqty
O000001Ayşe Yılmazayse.yilmaz@example.comKapadokya Bulut Mimarisi 441
O000001Ayşe Yılmazayse.yilmaz@example.comAnadolu Yün Kazak 951
O000001Ayşe Yılmazayse.yilmaz@example.comEge Hava Temizleyici 1423
O000001Ayşe Yılmazayse.yilmaz@example.comToros Python ile Veri 1792

The e-mail address of Ayşe is now in four rows. In the real shop, Ayşe has 30 orders, so the address is in about 80 rows. Ayşe changes her address. The program must change all 80 rows. If it changes 79 and fails on one, the table has two different addresses for one person. Which one is correct? Nobody knows. This is an {{ k.term("update anomaly") }}.

With four tables, the address of Ayşe is in one row of customers. A change touches one row, and every order sees the new address through the identifier C00001. This design rule is {{ k.term("normalization") }}: store each fact one time, in the table that owns it, and point to it with identifiers.

One copy in Lale Market is on purpose: order_items.unit_price. The price in products can change tomorrow. An order must keep the price that the customer paid on that day. So the order line stores its own copy of the price. This copy is a business rule, not a mistake.

{% call k.predict("Tomorrow the price of P0142 in the products table changes from 2,693.65 to 2,999.00. Look at the tables above. Does the total of order O000001 change?") %}

No. The order line for P0142 has its own unit_price (2,693.65). The orders row has its own total (14,988.97). Nothing in order O000001 reads products.price. Only new orders use the new price.

04JOIN: put the pieces of one order together again

Normalization splits the facts over four tables. A web page needs them together: "Order O000001, Ayşe Yılmaz, four products with names and prices". A {{ k.term("JOIN") }} combines rows of two tables into one result row when a condition is true. The usual condition is "the borrowed identifier in one table equals the owned identifier in the other table".

A simple picture first. You have a list of phone calls (caller number, minutes) and a phone book (number, name). To print "name, minutes", you take each call, find its number in the phone book, and write the name next to the minutes. This matching is a JOIN. The call list borrows the number, and the phone book owns it.

{% call k.sql("Q2", "Order O000001 with the customer name and the product names") %} 
SELECT o.order_id, o.order_date::date AS order_date, c.name AS customer,
       p.name AS product, oi.qty, oi.unit_price, oi.qty * oi.unit_price AS line_total
FROM orders o
JOIN customers   c  ON c.customer_id = o.customer_id
JOIN order_items oi ON oi.order_id   = o.order_id
JOIN products    p  ON p.product_id  = oi.product_id
WHERE o.order_id = 'O000001';
FROM orders oStart from the orders table. o is a short name (an alias) for it, so later lines can write o.customer_id instead of orders.customer_id.
JOIN customers c ON c.customer_id = o.customer_idFor each order row, find the customer row whose owned identifier equals the identifier that the order borrows. The result row now has the columns of both rows.
JOIN order_items oi ON oi.order_id = o.order_idFind every order line that borrows the order_id of this order. One order with four lines gives four result rows. The order and customer columns repeat in each of them.
JOIN products p ON p.product_id = oi.product_idFor each line, find the product that owns the product_id of the line. Now each result row also has the product name.
WHERE o.order_id = 'O000001'Keep only order O000001. PostgreSQL usually applies this filter first, so it joins one order and not all of them.
SELECT ... oi.qty * oi.unit_price AS line_totalThe result columns. A column can be a calculation. AS line_total gives the calculated column a name. ::date changes the date-and-time value into a date only.
{% endcall %} {% call k.predict("Look at the order_items table above. How many rows does this query return? Which columns repeat in every row?") %}

4 rows, because order O000001 has 4 lines. order_id, order_date and customer repeat in each row, because each row is one line together with its order and its customer. The result repeats data. The tables do not: each fact is still stored one time.

{% endcall %} {{ k.sim("join", "JOIN of orders, customers, order_items and products for O000001") }}

The order of the steps in the simulation is one correct plan. PostgreSQL has a component named the {{ k.term("planner") }}. It looks at the query, the table sizes and the indexes, and it selects the order of the joins and the join method. On large tables it can select a different order. The result is always the same. Only the work is different.

05Aggregation: many rows become one number

Until now, each result row came from input rows one to one. Some questions are different. "How much did the shop earn?" needs one number from many rows. A function that takes many values and returns one value is an {{ k.term("aggregate function") }}. The five common ones:

FunctionWhat it returnsExample on the qty column of order_items: 1, 1, 3, 2, 5, 10, 2, 1, 1
count(*)The number of rows9
sum(qty)The total of the values26
avg(qty)The average (sum divided by count)26 / 9 = 2.89
min(qty), max(qty)The smallest and the largest value1 and 10
count(DISTINCT order_id)The number of different values4 (O000001, O000102, O000103, O000104)

Without GROUP BY, an aggregate returns one row for the whole table. SELECT sum(qty) FROM order_items returns one row with 26.

GROUP BY: one result row for each group

The manager asks a more useful question: "How much did each category earn?" Now we need one number for each category, not one for the shop. {{ k.term("GROUP BY") }} first puts the rows into groups. Rows with the same value in the group column go into the same group. Then the aggregate functions run inside each group, and each group becomes one result row.

{% call k.callout("analogy", "Analogy") %}

You have a box of receipts and five empty envelopes, one for each category. You take the receipts one by one and put each one into the envelope of its category. Then you add up the amounts in each envelope and write the total on the envelope. The envelopes are the groups. The total on each envelope is the aggregate. A receipt of a cancelled order goes into the bin, not into an envelope. That is the WHERE filter.

{% endcall %}

The category is not in order_items. It is in products. The status is in orders. So the query first joins the three tables, and then it groups. This is what PostgreSQL sees after the JOINs, before the grouping. Each row is one order line with the category of its product and the status of its order:

{% for oid, pid, q, price in sample_data.order_items.rows %} {% set st = (sample_data.orders.rows | selectattr(0, "equalto", oid) | first)[3] %} {% set cat = (sample_data.products.rows | selectattr(0, "equalto", pid) | first)[2] %} {% endfor %}
The rows after FROM and JOIN (input of WHERE and GROUP BY)
order_idstatusproduct_idcategoryqtyunit_priceqty × unit_price
{{ oid }}{{ st }}{{ pid }}{{ cat }}{{ q }}{{ "{:,.2f}".format(price) }}{{ "{:,.2f}".format(q * price) }}
{% call k.sql("Q3", "Revenue of each category, the largest first") %} 
SELECT p.category,
       count(DISTINCT o.order_id)           AS orders,
       sum(oi.qty)                          AS pieces,
       round(sum(oi.qty * oi.unit_price), 2) AS revenue
FROM order_items oi
JOIN orders o   ON o.order_id = oi.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status <> 'cancelled'
GROUP BY p.category
ORDER BY revenue DESC;

You write a query in the order SELECT, FROM, WHERE, GROUP BY, ORDER BY. PostgreSQL works in a different order. Read the clauses in the order of the work:

1. FROM order_items oi JOIN orders o ... JOIN products p ...Build the rows of the table above: each order line with its order and its product. Nine rows.
2. WHERE o.status <> 'cancelled'<> means "is not equal to". Drop the rows of cancelled orders. The line of O000104 goes out. Eight rows stay.
3. GROUP BY p.categoryPut the eight rows into envelopes by category: Kitap, Elektronik, Ev & Yaşam, Moda.
4. SELECT p.category, count(...), sum(...), round(...)For each envelope, calculate the numbers. count(DISTINCT o.order_id) counts the different orders in the envelope, so an order with two books counts one time. sum(oi.qty * oi.unit_price) adds the line totals. round(..., 2) keeps two decimals.
5. ORDER BY revenue DESCSort the result rows by revenue. DESC means descending: the largest first.

A filter on the groups uses {{ k.term("HAVING") }}, not WHERE. WHERE drops input rows before the grouping. HAVING drops result groups after the grouping. Example: ... GROUP BY p.category HAVING sum(oi.qty * oi.unit_price) > 10000 keeps only the categories with more than 10,000 in revenue. In our data, that is Kitap and Elektronik.

This query must read every order line, because the question is about all of them. On the real shop, that is about 12,500 rows and takes a few milliseconds. On ten years of orders it can read hundreds of millions of rows, and it competes with the checkout for the same server. The Redshift tutorial shows a database that AWS built for this kind of question.

06Indexes: find a row without reading the table

Section 02 showed a Seq Scan: to find the İstanbul customers, PostgreSQL read every row. For a table of 15 pages, that is fine. For a table of 10 million customers (about 150,000 pages), each such query reads 150,000 pages. An index solves this.

An {{ k.term("index") }} is a second structure next to the table. It holds the values of one column (or several columns) in sorted order. Each entry of the index says where the row with that value is in the table. Because the index keeps the values in sorted order, PostgreSQL does not read them all. It jumps to the correct part of the list.

{% call k.callout("analogy", "Analogy") %}

A thick book has an index at the back. The words are in alphabetical order, and each word has a page number. To find "transaction", you do not read 600 pages. You open the index near "t", find the word in a few looks, and go to page 412. The book is the table. The alphabetical list is the index. The page number is the pointer to the row.

{% endcall %}

The default index type of PostgreSQL is the {{ k.term("B-tree") }} (PostgreSQL: Index Types). A B-tree is a sorted tree of pages. The top page (the root) says which page to read next for each range of values. Each page holds hundreds of keys, so a tree for 10 million keys has only 3 or 4 levels. A search reads one page on each level. Each primary key automatically gets a unique B-tree index (PostgreSQL: Constraints). For customers, its name is customers_pkey.

{{ k.fig("aurora-btree.png", "the root holds 7 and 16. To find 12, the search goes to the middle child, because 12 is between 7 and 16. In each node, the keys are in sorted order. One read on each level is enough.") }}

The simulation below shows the same idea with a sorted list of six identifiers. Each look at the middle of the remaining list takes half of it. This is how the search narrows down fast. A real B-tree takes away much more than half at each level, because each page holds hundreds of keys.

{{ k.sim("index", "Find C00005 with the primary key index customers_pkey") }}

An index is not free. Each INSERT must also add an entry to each index of the table. Each UPDATE of an indexed column must move the entry. Each index also uses disk and memory. So you add an index for the questions that the application asks often, not for every column. The planner can select a Seq Scan even when an index exists. This happens on a very small table, or when a filter matches most of the rows. Then a read of all pages in order is cheaper.

07Constraints: rules that the database enforces

An application can have bugs. A second application can write to the same database. A person can run a manual SQL command. A {{ k.term("constraint") }} is a rule in the schema. PostgreSQL checks it on every write, from every source, and refuses a write that breaks it. So the rule holds even when a program is wrong.

ConstraintThe ruleExample in Lale Market
NOT NULLThe value must be present.Each customer must have a name.
PRIMARY KEYThe value must be present and unique in the table.Two customers cannot both own C00003.
REFERENCES (foreign key)A borrowed value must exist as an owned value in the other table.An order line cannot point to product P9999 if no product owns it.
CHECK (...)A condition must be true for the row.CHECK (stock >= 0): the stock cannot go below zero.
{% call k.predict("Use the products table above. P0095 has stock 76. A program sends UPDATE products SET stock = stock - 500 WHERE product_id = 'P0095'. What happens to the row?") %}

Nothing. 76 - 500 = -424, which breaks CHECK (stock >= 0). PostgreSQL refuses the statement with an error, and the stock stays 76.

{% endcall %} {{ k.sim("constraints", "Three bad writes, three refusals") }}

The foreign key of order_items also has ON DELETE CASCADE toward orders: order_id text REFERENCES orders ON DELETE CASCADE. It means: when a program deletes an order, PostgreSQL also deletes the lines of that order. Without this clause, PostgreSQL would refuse to delete an order that still has lines, because the lines would then borrow an identifier that nobody owns.

08Transactions: all or nothing

Many business actions need more than one statement. The classic example is a bank transfer of 200 from Ayşe to Mert:

UPDATE accounts SET balance = balance - 200 WHERE owner = 'Ayşe';   -- Ayşe: 1,000 becomes 800
UPDATE accounts SET balance = balance + 200 WHERE owner = 'Mert';   -- Mert:   500 becomes 700

If the server stops between the two statements, 200 left Ayşe's account but did not arrive in Mert's account. The bank lost money. The two statements must happen together, or not at all.

A {{ k.term("transaction") }} groups statements into one unit. BEGIN starts it. COMMIT makes all its changes permanent and visible to others at the same moment. ROLLBACK undoes all its changes. If the server stops before COMMIT, PostgreSQL undoes the open transaction when it starts again (PostgreSQL: Transactions).

Database people describe the promises of a transaction with the four letters {{ k.term("ACID") }}:

LetterPromiseIn the bank example
AtomicityAll statements of the transaction happen, or none happens.Both balances change, or neither changes.
ConsistencyAfter the transaction, every constraint is still true.A CHECK (balance >= 0) refuses a transfer that makes Ayşe's balance negative.
IsolationTransactions that run at the same time do not see each other's unfinished changes.A report that runs during the transfer never sees 800 + 500.
DurabilityAfter COMMIT, the change survives a crash.A power failure one second after COMMIT does not undo the transfer.

The Lale Market checkout is the same kind of action. These are its real statements (from engines/aurora.py), one UPDATE for each cart line:

BEGIN;
UPDATE products SET stock = stock - 2 WHERE product_id = 'P0001' AND stock >= 2;
UPDATE products SET stock = stock - 1 WHERE product_id = 'P0142' AND stock >= 1;
INSERT INTO orders VALUES ('W1793...', 'C00006', '<visitor>', now(), 'processing', 9441.33);
INSERT INTO order_items VALUES ('W1793...', 'P0001', 2, 3373.84);
INSERT INTO order_items VALUES ('W1793...', 'P0142', 1, 2693.65);
COMMIT;

The last piece: two customers at the same time

Atomicity protects one transaction from a crash. A second danger comes from two transactions that run at the same time. Product P0095 has 1 piece left. Ayşe and Mert press "Place the order" in the same second. A naive program reads the stock first, decides in the application, and then writes the new value. Play the simulation and watch the "pieces sold" counter.

{{ k.sim("lost", "The naive way: read, decide, then write") }}

Both programs read 1 before either of them wrote. Each program calculated 1 - 1 = 0 and wrote 0. Two pieces left the shop, but the stock went down by one. The change of the first program is lost under the change of the second. This is a {{ k.term("lost update") }}.

The Lale Market checkout avoids it. It puts the test inside the UPDATE: SET stock = stock - 1 WHERE product_id = 'P0095' AND stock >= 1. An UPDATE takes a {{ k.term("row lock") }} on each row that it changes. The lock stays until the transaction ends. A second UPDATE of the same row waits for the lock. When the lock goes away, the second UPDATE tests the condition again on the new value.

{{ k.sim("locked", "The safe way: test and change in one UPDATE, under a row lock") }} {% call k.callout("analogy", "Analogy") %}

A café has one toilet with one key. The person who takes the key goes in. The next person waits at the door. When the key comes back, the next person goes in. That person sees the room as it is now, not as it was at the start of the wait. The row is the room, and the row lock is the key.

{% endcall %}

Readers do not wait for this key. PostgreSQL uses {{ k.term("MVCC") }} (multi-version concurrency control). An UPDATE does not overwrite the old row. It writes a new version of the row. Until COMMIT, other sessions still see the old version. Take a report that reads products during a checkout. It sees the stock from before the checkout, not a half-done state, and it does not wait (PostgreSQL: MVCC Introduction). PostgreSQL deletes old versions later, when no transaction can need them. This background work is VACUUM.

{{ k.quiz("aurora-q5", "Why does the checkout write AND stock >= 1 inside the UPDATE, and not run a SELECT first?", ["The SQL text is shorter and easier to read", "The test and the change happen under one row lock", "PostgreSQL does not allow SELECT inside a transaction", "The UPDATE can then skip the primary key index"], 1, "Between a SELECT and a later UPDATE, another transaction can change the row. A single UPDATE tests the condition and changes the row while it holds the row lock.") }}
Part 2

Amazon Aurora PostgreSQL: the AWS service

The same PostgreSQL, with a different storage layer and with the operations done by AWS.

09What you must do when you run PostgreSQL yourself

Everything in Part 1 works on one server: one machine with PostgreSQL and a disk. For a real shop, one server is not enough. You must solve these tasks yourself:

  1. The disk can fail. You need a copy of the data on a second machine, ideally in a second data center. PostgreSQL can stream its changes to a replica server, but you install it, watch it and keep it working yourself.
  2. The server can fail. Somebody, or some tool, must detect the failure, promote the replica to the new primary, and move the application to it.
  3. Reads grow. Each extra read replica is a full copy of the database. A 2 TB database needs 2 TB more disk for each replica, and hours to build it.
  4. The disk gets full. You must watch the space and make the disk larger before it is full.
  5. Backups. You must take backups, keep them in a different place, and test that a restore works.
  6. Upgrades and patches. You must update the operating system and PostgreSQL without long downtime.

None of these tasks is about your shop. Amazon Aurora takes most of them over.

10The design of Aurora: compute and storage are separate

On one server, PostgreSQL and its data are on the same machine. Aurora separates them into two layers:

  • The compute layer is one or more {{ k.term("DB instance") }}s. Each DB instance runs the PostgreSQL engine: it accepts connections, plans queries and runs transactions. Everything in Part 1 happens here.
  • The storage layer is the {{ k.term("cluster volume") }}. It is a single, virtual volume that spans several Availability Zones (AZs). An AZ is one or more separate data centers in an AWS Region, with its own power and network.

Together they form an Aurora {{ k.term("DB cluster") }}. The AWS documentation describes it like this (Amazon Aurora DB clusters):

  • Each cluster has one primary (writer) DB instance. It "supports read and write operations, and performs all of the data modifications to the cluster volume".
  • A cluster can have up to 15 Aurora Replicas (reader instances). They connect to the same storage volume and support only reads. If the writer becomes unavailable, Aurora fails over to one of them automatically.
  • The storage of each cluster "consists of six copies of all your data, spread across three AZs". This is true also when the cluster has only a writer (How Aurora serverless works).
{{ k.fig("aurora-cluster.png", "the writer instance and the two reader instances sit in three Availability Zones. All three connect to one shared storage volume, which keeps copies of the data in each zone. A reader does not keep its own copy. The volume also sends continuous backups to Amazon S3.") }}

Endpoints: where the application connects

An application does not connect to a machine name. It connects to an {{ k.term("endpoint") }}, a DNS name that Aurora keeps up to date:

  • The cluster endpoint (writer endpoint) always points to the current writer. Use it for all writes. After a failover, it points to the new writer.
  • The reader endpoint spreads connections over the Aurora Replicas. Use it for reports and other read-only work, so they do not slow down the writer.
  • Each instance also has its own instance endpoint, for special cases.

11Aurora in Lale Market

This is the real setup of the workshop (from cloudformation/workshop.yaml):

  • The cluster dbws-aurora runs Aurora PostgreSQL version 17.9 with encrypted storage.
  • It has two DB instances: dbws-aurora-writer in AZ a and dbws-aurora-reader in AZ b.
  • Both instances use Aurora Serverless v2 (instance class db.serverless). You do not select a server size. You give a capacity range in Aurora capacity units (ACUs). Each ACU is "approximately 2 gibibytes (GiB) of memory, corresponding CPU, and networking". Lale Market uses 0.5 to 4 ACUs. Aurora changes the capacity with the load, in steps as small as 0.5 ACU (How Aurora serverless works).
  • The Aurora Engine App connects to the writer endpoint on port 5432 with TLS. The password comes from AWS Secrets Manager. Only the security group of the Engine App can reach the database.
  • A zero-ETL integration copies the four tables to Amazon Redshift in near real time. The sales report of the shop uses that copy, so the large scans do not run on the checkout database.
