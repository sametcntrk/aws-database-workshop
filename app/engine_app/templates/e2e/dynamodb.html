00What you will learn

Lale Market keeps each shopping cart in Amazon DynamoDB. Each page reads the cart, the cart changes often, and it must stay fast at any number of shoppers. DynamoDB gives the same fast read at any table size, but only if you design the key for the questions that the app asks.

After this tutorial, you can do these tasks:

  1. Explain how the partition key decides where DynamoDB stores an item.
  2. Design a primary key (partition key + sort key) from a list of access patterns.
  3. Tell when to use GetItem, Query and Scan, and predict their cost in read request units.
  4. Use a condition and an atomic ADD to keep a rule without a lock.
  5. Say when DynamoDB is the correct Engine, and when a relational database is better.

01The model: items found by a key

A DynamoDB table holds {{ k.term("item", "item") }}s. An item is a set of attributes (name and value), like one JSON object. Two items in one table can have different attributes. Each item must have the {{ k.term("primary key") }}. The other attributes are free.

{{ k.fig("dynamodb-table.png", "item 101 has Phone, item 102 has Address, and item 103 has FavoriteColor and Address. Only the primary key PersonID is in each item. The table has no schema for the other attributes.") }}

The primary key has one or two parts:

  • Each table has a {{ k.term("partition key") }} (pk). DynamoDB uses it to select the storage partition of the item.
  • The {{ k.term("sort key") }} (sk) is optional. DynamoDB keeps the items with the same partition key together, sorted by the sort key.

This is the real table definition of Lale Market (from cloudformation/workshop.yaml):

TableName: dbws-cart
BillingMode: PAY_PER_REQUEST          # on-demand: no capacity plan, pay per request
KeySchema:
  - AttributeName: pk   KeyType: HASH     # partition key
  - AttributeName: sk   KeyType: RANGE    # sort key
TimeToLiveSpecification: { AttributeName: expires_at, Enabled: true }
{% call k.query("dynamodb", "D1", "Describe the table") %} 
client.describe_table(TableName='dbws-cart')

Purpose: see the key schema and the capacity mode. ItemCount is approximate. DynamoDB updates it about every six hours.

{% endcall %}

02Partitions: why a key lookup stays fast

DynamoDB spreads a table over many {{ k.term("partition") }}s. A partition is a unit of storage on SSDs, with copies in more than one Availability Zone. To store an item, DynamoDB gives the partition key value to a hash function. The output selects the partition (Partitions and data distribution).

{{ k.fig("dynamodb-hash-table.png", "a hash function changes a key (John Smith) into a slot number (873). The same key always gives the same number, so a lookup goes straight to one slot. DynamoDB uses the same idea to go from a partition key to one partition.") }} {{ k.fig("dynamodb-partition-key.png", "the item with AnimalType Dog goes into the third partition, because the hash of \"Dog\" points there. To read it, DynamoDB calculates the same hash and reads only that partition.") }}

This is the core trade of DynamoDB. A read with the full key is one hash and one partition read, at any table size. A question that does not give the key has no partition to go to. It must read the full table.

{% call k.callout("analogy", "Analogy") %}

A cloakroom gives you a numbered ticket. With the ticket, the attendant goes straight to one hook, if the room has 100 coats or 100,000 coats. Without the ticket ("the blue coat with a scarf"), the attendant must look at each hook. The partition key is the ticket.

{% endcall %}

Each partition can serve at most 3,000 read units and 1,000 write units per second (Partition key design). So a good partition key has many different values, and the traffic spreads over them. A key with few values (for example, the country) puts the load on few partitions. This is a {{ k.term("hot partition") }}.

{{ k.quiz("ddb-q1", "Which partition key spreads the Lale Market cart traffic best?", ["The city of the shopper", "The browser id of the shopper", "The date of the cart", "The category of the product"], 1, "Each Visitor has a different browser id, so the carts spread over many partition key values. City, date and category have few values, and some values are very busy.") }}

03Design the key from the questions

In a relational database, you design the tables first, and you write any query later. In DynamoDB, you list the {{ k.term("access pattern") }}s first. An access pattern is a question that the app asks, with the values that it knows at that moment. Then you design the key so that each question is one GetItem or one Query.

Access pattern of the cartThe app knowsOperation
Show my cartmy browser idQuery pk = CART#<browser id>
Change the quantity of one productbrowser id, product idUpdateItem pk + sk = ITEM#<product id>
Delete one product from the cartbrowser id, product idDeleteItem pk + sk
Empty the cart after checkoutbrowser idQuery, then BatchWriteItem (delete)

So Lale Market uses pk = CART#<browser id> and sk = ITEM#<product id>. All items of one cart are in one item collection, sorted by product id. This is the tutorial cart that the queries below write and read:

The prefixes CART# and ITEM# are a convention. They let one table hold different kinds of items without a key collision. The Load Simulation, for example, writes items with pk = SIM#... into the same table.

04Write and read: PutItem, GetItem, Query

{% call k.query("dynamodb", "D2", "Write the three items of the tutorial cart") %} 
table.put_item(Item={'pk': 'CART#tutorial-demo', 'sk': 'ITEM#P0001', 'name': 'Alpen Kablosuz Kulaklık 1',
                     'qty': 2, 'unit_price': 3373.84, 'expires_at': <now + 86400>})
# ... and the same for ITEM#P0044 and ITEM#P0142

Purpose: put the example data into the table. PutItem replaces an item with the same pk and sk, so the result is the same each time you run it. A write of an item up to 1 KB costs one {{ k.term("write request unit") }} (WRU).

{% endcall %} {% call k.query("dynamodb", "D5", "Read one item with the full primary key") %} 
table.get_item(Key={'pk': 'CART#tutorial-demo', 'sk': 'ITEM#P0044'})

Purpose: read exactly one item. GetItem needs both parts of the key. It returns zero or one item.

{% endcall %} {% call k.predict("The tutorial cart has three items, each smaller than 1 KB. A strongly consistent Query reads all three. How many read request units does it cost?") %}

1 RRU. A Query adds the sizes of all items that it reads, then rounds the total up to the next 4 KB. Three small items are far below 4 KB. One strongly consistent read of up to 4 KB costs 1 read unit (Read and write operations). Three GetItem calls would cost 3 RRU, one for each item.

{% endcall %} {% call k.query("dynamodb", "D3", "Show the cart: Query one partition key (strongly consistent)") %} 
table.query(KeyConditionExpression=Key('pk').eq('CART#tutorial-demo'),
            ConsistentRead=True, ReturnConsumedCapacity='TOTAL')
  1. Hash CART#tutorial-demo to find the partition.
  2. Go to the start of the item collection of that key.
  3. Read the items in sort key order until the collection ends (or a limit or 1 MB of data).
{% endcall %} {% call k.query("dynamodb", "D6", "Query with a sort key condition") %} 
table.query(KeyConditionExpression=Key('pk').eq('CART#tutorial-demo')
                                   & Key('sk').between('ITEM#P0001', 'ITEM#P0099'))

Purpose: read a range inside one item collection. The sort key condition can be =, <, >, between or begins_with. Because DynamoDB keeps the items in sort key order, it reads only the range. The result has P0001 and P0044, but not P0142.

{% endcall %} {{ k.quiz("ddb-q2", "Which request can DynamoDB answer with a Query on this table?", ["All carts that contain product P0044", "All carts with a total above 5,000", "All items of the cart of one browser id", "All items that expire in the next hour"], 2, "A Query needs one partition key value. Only the cart of one browser id gives it. The other three questions do not know the partition key.") }}

05Scan: the question without a key

"Which carts have two or more pieces of a product?" This question gives no partition key. The only operation that can answer it is a {{ k.term("Scan") }}. A Scan reads each item of the table, page by page. A filter expression drops items after the read, so you pay for each item that DynamoDB read, not only for the items that you get.

{% call k.query("dynamodb", "D7", "Count the items with qty >= 2 (full Scan)") %} 
table.scan(Select='COUNT', FilterExpression=Attr('qty').gte(2))   # repeat with ExclusiveStartKey until the last page

Compare ScannedCount (items read) with Count (items that match). The read request units follow ScannedCount. On a table of a billion items, this question costs a billion item reads.

{% endcall %}

If the app needs this question often, you add a {{ k.term("global secondary index") }} (GSI). A GSI is a copy of selected attributes with a different key. DynamoDB keeps the copy up to date for you. Each write to the table then also writes to the index. The Lale Market cart table has no GSI, because the cart has no such question.

{{ k.fig("dynamodb-gsi.png", "the index GameTitleIndex has the partition key GameTitle and the sort key TopScore. \"Top scores of Galaxy Invaders\" is now one Query. On the base table, keyed by UserId, the same question needs a Scan.") }}

06Read consistency and capacity

DynamoDB keeps copies of each partition in more than one Availability Zone. A write goes to the copies, and the copies agree after a short time.

  • A {{ k.term("strongly consistent read") }} returns the result of all writes that succeeded before the read. It costs 1 read unit per 4 KB.
  • An {{ k.term("eventually consistent read") }} can miss a very new write. It costs one half read unit per 4 KB. It is the default.
{% call k.query("dynamodb", "D4", "The same Query, eventually consistent") %} 
table.query(KeyConditionExpression=Key('pk').eq('CART#tutorial-demo'),
            ConsistentRead=False, ReturnConsumedCapacity='TOTAL')

Compare the consumed units with D3. The result is the same here, because nobody wrote in the last second.

{% endcall %}

Lale Market reads the cart strongly consistent at checkout, because the order must have the last quantity. The cart page lets you try both modes.

07Rules without locks: conditions and atomic ADD

DynamoDB has no SELECT ... then UPDATE with a row lock. Instead, a write can carry a {{ k.term("condition expression") }}. DynamoDB tests the condition and writes in one step. If the condition is false, DynamoDB does not write and returns ConditionalCheckFailedException.

The Lale Market rule is "at most 5 pieces of one product in a cart". This is the real request of the product page (from engines/dynamodb.py):

table.update_item(
  Key={'pk': 'CART#<browser id>', 'sk': 'ITEM#P0001'},
  UpdateExpression='ADD qty :q SET #n = :n, unit_price = :p, expires_at = :e',
  ConditionExpression='attribute_not_exists(qty) OR qty <= :max',   # :max = 5 - :q
  ReturnConsumedCapacity='TOTAL')
{% call k.predict("The tutorial item ITEM#P0001 has qty 2. A request adds 5. The condition is qty <= 0 (5 - 5). What does DynamoDB do?") %}

It refuses the write. 2 <= 0 is false. The item keeps qty 2. The refused write still costs write units, because DynamoDB read the item to test the condition.

{% endcall %} {% call k.query("dynamodb", "D8", "A conditional write that DynamoDB refuses") %} 
table.update_item(Key={'pk': 'CART#tutorial-demo', 'sk': 'ITEM#P0001'},
                  UpdateExpression='ADD qty :q',
                  ConditionExpression='attribute_not_exists(qty) OR qty <= :max',
                  ExpressionAttributeValues={':q': 5, ':max': 0})
{% endcall %}

ADD is also an atomic counter. Two requests that add at the same time do not lose an update, because DynamoDB applies each ADD to the current value.

{% call k.query("dynamodb", "D9", "Atomic ADD") %} 
table.update_item(Key={'pk': 'CART#tutorial-demo', 'sk': 'ITEM#P0044'},
                  UpdateExpression='ADD qty :one', ReturnValues='UPDATED_NEW')

Run it two times. The quantity goes up by one each time. Run D2 to reset the tutorial cart.

{% endcall %} {{ k.quiz("ddb-q3", "Why does the cart rule use a ConditionExpression, and not a GetItem before the UpdateItem?", ["A GetItem costs more than an UpdateItem", "The test and the write happen in one step", "UpdateItem cannot read the current value", "A condition makes the write strongly consistent"], 1, "Between a GetItem and a later UpdateItem, a second tab can add pieces. DynamoDB tests the condition at the moment of the write.") }}

08Time to live: carts that delete themselves

An abandoned cart is useless after a day. Each cart item has expires_at, a Unix time in seconds. The table has {{ k.term("TTL") }} on this attribute. DynamoDB deletes expired items "within a few days of their expiration time, without consuming write throughput" (Time to live). Until the delete, an expired item can still appear in a read. An app that must not show it uses a filter on expires_at.
