Part A

Foundations: the key-value idea, with all its cases

How a database that finds data only by key stays fast at any size, and what it gives up in return. This part first defines each concept. Then it shows all cases of that concept in one table. So no question stays open: the answer to "what if ...?" is in the table. The ideas are the same in every key-value database. The names are the standard names, and they do not change until the end of the page.

A1Why a key-value database? The cloakroom

A theatre has a cloakroom with 5,000 hooks. When you leave your coat, you get a ticket with a number. At the end of the play, 5,000 people come back at the same time. With a ticket, an attendant walks straight to one hook. The time is the same for hook 12 and for hook 4,812. Without a ticket ("a blue coat with a red scarf"), the attendant must look at every hook. That takes a long time, and the queue grows.

{% call k.callout("analogy", "Analogy") %}

The ticket number is the key. The coat on the hook is the value. A key-value database is a cloakroom: it is very fast when you bring the ticket, and slow when you only describe the coat. A large theatre adds more attendants and splits the hooks into rooms. Section A4 gives these rooms their technical name.

{% endcall %}

A relational database (see the Aurora tutorial) can answer any question with SQL. The price is that one server runs all writes, and the planner must decide how to answer each new question. A key-value database makes a different trade. It answers only questions by key. In return, it can split the data over many machines, and each machine answers its share alone. So the speed of one request does not depend on the size of the table.

A3The composite primary key: partition key and sort key, with all combinations

A cart is not one value. It is a group of rows: one row for each product. The visitor wants to read the whole group in one request, and to change one row without a touch on the other rows. A simple primary key cannot do both. Either the full cart is one value, and the full cart is rewritten for one row. Or each row is a separate key, and you must know all keys to read the full cart. The composite primary key solves this.

{% call k.ask("Why do the keys start with CART# and ITEM#? Is this a rule of the database?") %}

No, it is a convention of the designer. The prefix tells a person what kind of thing the key names. So one table can hold several kinds of values (cart rows, coupons) with no confusion. The database only sees a text, for example CART#7f3a. A key with no prefix works the same way.

{% endcall %} {% call k.ask("Can I reverse the order by sort key, for example the newest event first?") %}

Yes. The order comes from the sort key, and a read request can ask for this order forward or backward. The database does not sort the values again. It only reads the group from its end to its start. So the question "the newest 50 events" is also cheap.

{% endcall %} {% call k.ask("Can a key have three parts?") %}

In the standard model, no: there are at most two parts, the partition key and the sort key. If you need a third level, you put it inside the sort key, as in the last row of the table above. Cassandra permits more than one clustering column. In DynamoDB the sort key is one field, and several parts are joined in one text.

A6Write paths: every write needs the full primary key

For a read, a part of the key was enough. For a write, the situation is different: every write and every delete needs the full primary key. The database does not accept a request such as "delete all of this group" or "change the values whose sort key starts with ...". To change many values, you first read the group, then you write each value one by one. For a reader who comes from a relational database, this is the most surprising rule. There, DELETE FROM cart WHERE visitor = '7f3a' is one statement.

The architect's view: when key-value, when DynamoDB

In short: a key-value database answers each request by key, very fast, at any size and at any request rate. You get this speed only if you know your questions in advance and design the key for them.

F1 · Direct read and write by key
What it givesThe application gives the key that it has. The database finds the partition by hash and reads or writes one value. The time of this path does not depend on the number of values in the table. It is the same few milliseconds in the teaching table of 8 values and in the file metadata table of 2 billion values. There is no index scan, no plan selection and no wait for a lock.
Which signal calls itThe application already knows the key on each request. Examples: get the cart with the visitor id from the cookie. Get the profile with the user id from the login. Write the last state with the device id from the message. If a request starts with a "search" and not with a key, this signal is absent.
Its limitEach question that does not know the key is expensive: "sessions whose last_page is /cart" needs a read of the whole table. There is no search, no sort and no sum by the content of the value. If one question in two has no key, this model is in the wrong place.
When an alternative is betterIf the questions are not known in advance or change each month, a relational database (SQL asks on any column). If a text search with typo tolerance and relevance is wanted, a search engine. If flexible queries on the content of the value are the main work, a document database.
F2 · Split into partitions by hash
What it givesThe data and the traffic spread over many machines by the hash of the partition key. When the traffic doubles, a machine (or, in a managed service, a partition) is added, and each request is still answered in one partition. The 50-times jump of a campaign night is not an architecture problem but a capacity problem, and in a managed service even that is automatic.
Which signal calls itThe traffic is very large or very variable. Examples: 60,000 reads per second for three hours on a sale night. One million players on the release day, 100,000 one month later. Two million devices write every 30 seconds. Or the growth cannot be planned: "the number of users doubles each year".
Its limitEach request must stay in one partition. So there is no JOIN, no foreign key between tables and no "GROUP BY over all partitions". A few busy keys (city, date, campaign product) make a hot partition: one partition hits its limit while the others wait empty. The spread comes from the key design. The service does not correct it for you.
When an alternative is betterIs the traffic within reach of one strong server (a few thousand writes per second)? Are relations, rules or reports wanted? Then a relational database gives more for a lower price. For sums and groups over all data of a year, a data warehouse.
F3 · Composite primary key: group and sorted range
What it givesThe many related values of one thing stay together under the same partition key, in sort key order. Examples: the rows of a cart, the events of a visitor, the items of a player. One request reads the whole group, a prefix slice ("only WEAPON#") or a range ("October"), sorted. The question "the newest 50" is equally cheap with the reverse order and a limit.
Which signal calls itAll rows of this cart, in product order. The last 50 events of this visitor. The files of this user in folder X, by name. All seats of this event. If there are many small records under one owner, and these records have an order, the signal is here.
Its limitThe order is only by the sort key. "Cart rows sorted by price" needs a second index. The group stays in one partition: one group of a million rows tires that partition and cannot be split. There is no bulk delete and no bulk update on a group. Each value is written one by one.
When an alternative is betterIs the same data often queried in several different orders (by date, by amount, by status)? Then the indexes of a relational database are more economical. If the group is an array inside a document and flexible updates inside the array are wanted, a document database. If the team already uses Cassandra, wide-column gives the same model with CQL.
F4 · Schemaless value
What it givesEach value carries its own fields. A cart row, a coupon and a gift note are side by side in the same table. A new field is written only to new values. The old values do not change, and there is no migration window. The field that the marketing team adds each quarter is not a database project.
Which signal calls itThe shape of the values differs by type: damage for a sword, duration for a potion, resolution for an image, page count for a document. Or it changes often: a new kind of value in each game update, a new profile field each quarter.
Its limitThe database does not check the inside of the value: required fields, types and foreign keys are the work of the application. Values written by two different versions mix in the same table, and the code that reads must know both shapes. The value has a size limit (400 KB in DynamoDB). Growing fields (history, log) go to a separate table.
When an alternative is betterDo the fields stay the same, and are the rules strict (invoices, accounting)? Then the schema of a relational database is a guarantee, not a burden. If the value is a long nested document, and queries on its content and partial updates are the main work, a document database.
F5 · Atomic and conditional write on one key
What it givesA rule is written as a condition inside the write, and the database tests it at the moment of the write. Examples: write if absent. Write if qty + 2 ≤ 5. Set delivered if status = shipped. Write if version = 7, and set it to 8. A counter increment is done in one step, with no read. Even if two requests race, the result is right: in the increment both are counted, in the condition the second one is rejected. There is no lock, no transaction and no "read first, then write".
Which signal calls itSimple rules on one value. At most 5 units of one product. Hold the seat only if free. Do not process the same request id twice. 100 requests per minute. If the rule stays inside one key, the signal is here.
Its limitIf the rule covers several values (seat + order + payment), a condition is not enough. A transaction is necessary, and it is limited (100 values in DynamoDB) and costs two times a normal write. There is no rule between tables (foreign key, total stock). A rejected conditional write also uses capacity.
When an alternative is betterDoes the rule cover several tables at once (cart + stock + order in one transaction)? Then the row lock and the transaction of a relational database are the simplest and the best solution. If the rule must run in memory in microseconds and loss is accepted, an in-memory store (SET NX, INCR).
F6 · Expiry (TTL)
What it givesEach value carries its own expiry time, and the database deletes it by itself. The application writes no delete request and operates no cleanup job. For a session, a temporary hold, an idempotency mark and an abandoned cart, this is the practical solution. It replaces the missing "delete of a whole group" (A6).
Which signal calls itData that must delete itself. A cart after one day. A session after 30 minutes. A seat hold after 10 minutes. A request id after 24 hours. A counter when the minute ends. If the lifetime of the data is known at the moment of the write, the signal is here.
Its limitNot exact in every store: DynamoDB usually deletes an expired value within a few days. The application may have to compare the time itself on each read. A renewal is a write, and 40,000 renewals per second are 40,000 write units. The expiry is per value, not per group or per table.
When an alternative is betterMust the expiry be exact to the second, and must expired data never be read (session, lock, rate limit)? Then use the EXPIRE of an in-memory store. If the deletion is a business rule with an audit trail (invoice retention), a scheduled job in a relational database.
F7 · Second index
What it givesThe same values are stored a second time with a different key, and the database updates the copy on each write. A known second question becomes a direct read in the index instead of a read of the whole table. Examples: in which carts is P0044? My files with the tag invoice.
Which signal calls itA few known questions, with different keys: by cart and by product, by user and by tag, by player and by score (leaderboard). If the questions are few and known in advance, the signal is here.
Its limitEach index adds cost and storage to each write: ten indexes mean ten times the writes. An index is also read by key. There is still no JOIN, no GROUP BY and no free filter. The copy can be eventually consistent: a reader just after a write can see the old value. If the questions are not known in advance, no index can be built.
When an alternative is betterIf the questions are many and variable, a relational database (an index on each column, the planner selects). If a text search and relevance are wanted, a search engine. DynamoDB offers a zero-ETL copy to OpenSearch for this. A document database is more comfortable with flexible indexes on fields inside the document.
F8 · Change stream
What it givesEach write (insert, change, delete) goes out in order as an event. Other programs read this stream and react: email, search index, analytics copy, alarm. The code that writes to the table knows nothing about these reactions. Reactions are added and deleted, and the write path does not change.
Which signal calls itReactions separate from the code that writes. An alarm for a meter above 80 degrees. A welcome email for a new customer. Update the search index when the metadata changes. Feed the activity history to the fraud check.
Its limitThe records are kept for a limited time (24 hours in DynamoDB). A consumer that does not read in this time loses them. The changes of one key are in order, but between different keys the order is not guaranteed. A stream is not a query: the question "all changes of yesterday" is answered from a stored copy, not from the stream.
When an alternative is betterMust events be kept for days, be read from the start by many consumers, and scale to millions of events per second? Then use a streaming platform (Kinesis, MSK). If analysis is wanted and not a reaction, an analytics copy (zero-ETL to Redshift).

M4The questions that an architect asks, in this order

  1. Can you list every access pattern now? If yes, a key-value database can serve each one with a key. If the questions are open, prefer a relational database.
  2. Which value does the application know at each request? That value is a candidate for the partition key.
  3. Does the partition key have many different values, used evenly? One busy value can become a hot partition.
  4. Which order must the results have? The order comes from the sort key (F3).
  5. Which rules must hold? One value: a condition. A few values: a transaction, if the product has one. Rules between tables: a relational database.
  6. Must the data survive a failure, or is it a copy? A durable record needs a durable store. A copy can live in memory.
  7. How fast? Microseconds point to an in-memory store. Single-digit milliseconds at any scale point to a durable key-value service.
  8. Who will operate it, and what does the team know? Serverless or nodes, a new API or a known one.

Part C

The AWS service: what DynamoDB runs for you

What you must do when you run a key-value store yourself, and what AWS does instead.

C1What you must do when you run a key-value store yourself

Open-source key-value and wide-column databases (for example Apache Cassandra) use the same partition idea. When you run one yourself, you must solve these tasks:

  1. Machines. Select, buy or rent the servers, and install the database on each one.
  2. Copies. Keep each partition on several machines in different data centers, and build a new copy after a failure.
  3. Growth. Add machines when the data grows, and move partitions to them without downtime.
  4. Capacity. Plan for the peak of the year. Machines that wait for the peak cost money all year.
  5. Backups and patches. Back up each node, test a restore, and update the software of every node.

C2What DynamoDB does for you

DynamoDB is serverless. You create a table and send requests. You never see a server. DynamoDB stores each partition in more than one Availability Zone, adds partitions when the data or the traffic grows, and moves the data for you.

TaskYour own key-value clusterAmazon DynamoDB
MachinesYou select and operate them.None to see. You work with tables and requests.
Copies in several data centersYou configure the replication and keep it working.DynamoDB keeps the copies in several Availability Zones.
GrowthYou add nodes and move data.DynamoDB adds partitions and moves data by itself.
Peak trafficYou buy machines for the peak.On-demand mode charges per request. Provisioned mode with auto scaling follows the load.
BackupsYou plan, store and test them.Point-in-time recovery and on-demand backups, with no load on the table.
Several RegionsYou build the replication and the conflict handling.Global tables replicate to other Regions, and any replica can take writes.

The options of M5 (DAX, global tables, Streams, zero-ETL) are all parts of the same service. You turn them on for a table. You do not install them.

C3DynamoDB in TDS Academy Market

  • One table, dbws-cart, in on-demand mode, with point-in-time recovery, TTL on expires_at and encryption at rest.
  • The DynamoDB Engine App runs on an EC2 instance in a private subnet. It reaches DynamoDB through a gateway VPC endpoint, so the traffic does not go to the internet.
  • Authentication uses the IAM role of the instance (SigV4). There is no password. The role allows only the cart table and only the actions that the app uses.
  • The cart page has two experiments: strongly or eventually consistent reads, and a Load Simulation that writes from 200 synthetic shoppers in parallel.
