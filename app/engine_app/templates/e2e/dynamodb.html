Part A

Foundations: the key-value idea

How a database that finds data only by key can stay fast at any size. These ideas are the same in every key-value database.

A1Why a key-value database? The cloakroom

A theatre has a cloakroom with 5,000 hooks. When you leave your coat, you get a ticket with a number. At the end of the play, 5,000 people come back at the same time. With a ticket, an attendant walks straight to one hook. The time is the same for hook 12 and for hook 4,812. Without a ticket ("a blue coat with a red scarf"), the attendant must look at every hook. That takes a long time, and the queue grows.

{% call k.callout("analogy", "Analogy") %}

The ticket number is the key. The hook is the place where the data lives. A key-value database is a cloakroom: it is very fast when you bring the ticket, and slow when you only describe the coat. A large theatre adds more attendants and splits the hooks into rooms. That is a partition.

{% endcall %}

A relational database (see the Aurora tutorial) can answer any question with SQL. The price is that one server runs all writes, and the planner must decide how to answer each new question. A key-value database makes a different trade. It answers only questions by key. In return, it can split the data over many machines, and each machine answers its share alone. So the speed of one request does not depend on the size of the table.

A2Keys and values: the model

A key-value database stores pairs. The key is a unique name, and the value is the data that belongs to that name. The database does not need to understand the value. It only needs the key to find it.

Many key-value databases let the key have two parts:

  • The partition part of the key decides where the data lives. All values with the same partition part are stored together.
  • The sort part of the key is optional. It decides the order of the values inside one partition, so the database can read a range: "the first three", "everything after this date".

Two parts together are a composite key. All values with the same partition part form one group, which the database can read in one request.

Different products use different names for the same ideas. The names matter only when you write code. The ideas are the same:

A3Partitions and hashing: why a lookup by key stays fast

A key-value database spreads its data over many {{ k.term("partition") }}s. A partition is a unit of storage with its own share of the data and its own share of the work. To place a value, the database gives the partition part of the key to a hash function. A {{ k.term("hash function") }} turns any value into a number, and the same value always gives the same number. The number selects the partition. Redis Cluster calculates a hash slot from the key. Cassandra calculates a token. DynamoDB uses its own internal hash. The idea is the same.

{{ k.fig("dynamodb-hash-table.png", "a hash function turns a name (John Smith) into a slot number (873). To find John Smith again, the program calculates the same number and goes straight to that slot. A key-value database uses the same idea to go from a key to a partition.") }} {% call k.predict("Look at the teaching table. Three partitions, and four carts. Is it possible that two carts land in the same partition? Does that break anything?") %}

Yes, two carts can land in the same partition. Nothing breaks. A partition holds many groups. Inside the partition, each group stays together and sorted by sk. The hash only decides which partition does the work for a key.

{% endcall %} {{ k.sim("hash", "Eight values, three partitions, one hash") }}

The simulation uses a small teaching hash (the sum of the character codes, modulo 3). Real databases use better hash functions, and the number of partitions grows as the data grows. The idea is the same: the key alone decides the partition, so the database does not need to look anywhere else.

Each partition can do only a limited amount of work per second. So a good partition key has many different values, and the requests spread evenly over them. If one value gets most of the traffic, its partition reaches its limit while the others are idle. This is a {{ k.term("hot partition") }}.

{{ k.quiz("ddb-q1", "Which partition key spreads the cart traffic of Lale Market best?", ["The city of the visitor", "The browser id of the visitor", "The date of the cart", "The category of the product"], 1, "Each visitor has a different browser id, so the traffic spreads over very many key values. The city, the date and the category have few values, and some values are very busy.") }}
Architect's view

The architect's view: when key-value, and when DynamoDB

First the category: when a key-value database is the right choice. Then the options on AWS, and when DynamoDB is the one to select.

In short: a key-value database answers each request by key, very fast, at any size and at any request rate. You get this speed only if you know your questions in advance and design the key for them.

The important word is {{ k.term("access pattern") }}. An access pattern is a question that the application asks, together with the values that it knows at that moment. "Show the cart of the browser with id 7f3a" is an access pattern. "Show all carts that contain a book, sorted by value" is a different access pattern. A key-value database answers the first one with one cheap request. For the second one it needs either a special index or a full read of the data.

M4The questions that an architect asks, in this order

  1. Can you list every access pattern now? If yes, a key-value database can serve each one with a key. If the questions are open, prefer a relational database.
  2. Which value does the application know at each request? That value is a candidate for the partition key.
  3. Does the partition key have many different values, used evenly? One busy value can become a hot partition.
  4. Which order must the results have? The order comes from the sort part of the key.
  5. Which rules must hold? One value: a condition. A few values: a transaction, if the product has one. Rules between tables: a relational database.
  6. Must the data survive a failure, or is it a copy? A durable record needs a durable store. A copy can live in memory.
  7. How fast? Microseconds point to an in-memory store. Single-digit milliseconds at any scale point to a durable key-value service.
  8. Who will operate it, and what does the team know? Serverless or nodes, a new API or a known one.

M6Where DynamoDB sits in Lale Market

Lale Market keeps every shopping cart in the table dbws-cart. The product page adds items. The cart page reads them. Checkout reads the cart strongly consistent, and Aurora writes the order. After the commit, the browser empties the cart in DynamoDB. The cart is a good fit. Every request knows the visitor id, and the carts are independent of each other. A lost cart after 24 hours costs nothing. The order is not a good fit for a key-value database in this shop, because it needs rules over stock, orders and lines together. That is the job of Aurora.

Part B

Deep dive: DynamoDB in practice

The DynamoDB names for the ideas of Part A, the read and write operations, key design and the extra features.

B1Items, attributes and the primary key in DynamoDB

A DynamoDB table holds {{ k.term("item", "item") }}s. An item is a set of attributes: a name and a value each, like one JSON object. Two items in one table can have different attributes. Only the {{ k.term("primary key") }} must be in each item.

{{ k.fig("dynamodb-table.png", "item 101 has Phone, item 102 has Address, and item 103 has FavoriteColor and Address. Only the primary key PersonID is in each item. The table has no schema for the other attributes.") }}

The two parts of the key from A2 have these names in DynamoDB: the {{ k.term("partition key") }} and the {{ k.term("sort key") }}. All items with the same partition key form an {{ k.term("item collection") }}. This is the real definition of the Lale Market table (from cloudformation/workshop.yaml):

Each DynamoDB partition "is designed to deliver a maximum capacity of 3,000 read units per second and 1,000 write units per second" (Partition key design). This is the limit behind the hot partition of A3.

B2Reads: GetItem, Query and Scan, and what they cost

DynamoDB has three ways to read. They differ in one thing: how much of the key the request gives.

OperationWhat the request givesWhat DynamoDB reads
GetItemThe full primary key (pk and sk)Exactly one item, or nothing
QueryThe partition key, and optionally a condition on the sort keyOne item collection, or a range of it, in sort key order
ScanNo key at allEvery item of the table, page by page
{% call k.sql("Q1", "Show the cart of visitor 7f3a") %} 
table.query(
    KeyConditionExpression=Key('pk').eq('CART#7f3a'),
    ConsistentRead=True,
    ReturnConsumedCapacity='TOTAL')
table.query(...)The Query operation of the AWS SDK for Python (boto3), on the table dbws-cart.
KeyConditionExpression=Key('pk').eq('CART#7f3a')The partition key must equal CART#7f3a. A Query must always name one partition key value.
ConsistentRead=TrueA strongly consistent read: the answer contains every write that succeeded before the read. The default is an eventually consistent read.
ReturnConsumedCapacity='TOTAL'Ask DynamoDB to report the read units that this request used. The Behind-the-scenes panel of the shop shows this number.
{% endcall %} {% call k.sql("Q2", "Every cart line with two or more pieces (a Scan)") %} 
table.scan(FilterExpression=Attr('qty').gte(2))
table.scan(...)Read the table from the first item to the last, page by page (up to 1 MB per page).
FilterExpression=Attr('qty').gte(2)After the read, keep only the items with qty >= 2. The filter does not reduce the read. You pay for every item that DynamoDB read.
{% endcall %}

The cost unit for reads is the {{ k.term("read request unit") }} (RRU) in on-demand mode. The rules (Read and write operations):

  • A strongly consistent read of up to 4 KB costs one read unit. An eventually consistent read of up to 4 KB costs one half.
  • A Query adds the sizes of all items that it reads and rounds the total up to the next 4 KB.
  • A Scan "considers the size of the items that are evaluated, not the size of the items returned".
{% call k.predict("Use the teaching table. The Query of CART#7f3a reads how many items? The Scan with qty >= 2 reads how many, and returns how many?") %}

The Query reads the 3 items of CART#7f3a, and returns 3. The Scan reads all 8 items and returns the 5 items with qty of 2 or more. All items here are small, so the Query costs 1 read unit when it is strongly consistent. The Scan pays for 8 items, not for 5.

{% endcall %} {{ k.sim("queryscan", "Query one cart, then Scan the table") }}

An eventually consistent read can miss a write from the last moment. Lale Market reads the cart eventually consistent for a quick preview, and strongly consistent at checkout, because the order must contain the last quantity.

B3Writes: rules without a lock

DynamoDB has no "SELECT, then UPDATE under a row lock". Instead, a write can carry a {{ k.term("condition expression") }}. DynamoDB tests the condition on the current item and writes in one step. If the condition is false, it does not write, and it returns ConditionalCheckFailedException.

The rule of Lale Market is: at most 5 pieces of one product in a cart. This is the real request of the product page (from engines/dynamodb.py):

{% call k.sql("Q3", "Add pieces to a cart line, with the limit of 5") %} 
table.update_item(
    Key={'pk': 'CART#7f3a', 'sk': 'ITEM#P0001'},
    UpdateExpression='ADD qty :q SET #n = :n, unit_price = :p, expires_at = :e',
    ConditionExpression='attribute_not_exists(qty) OR qty <= :max',   # :max = 5 - :q
    ReturnConsumedCapacity='TOTAL')
Key={'pk': ..., 'sk': ...}The full primary key of one item. UpdateItem changes the item, or creates it if it does not exist.
ADD qty :qAdd the number :q to the current value of qty. If two requests add at the same time, DynamoDB applies both. No addition is lost.
SET #n = :n, unit_price = :p, expires_at = :eWrite the name, the price and the new expiry time. #n stands for the attribute name name, because "name" is a reserved word.
ConditionExpression='attribute_not_exists(qty) OR qty <= :max'Write only if the line is new, or if the current quantity leaves room for the new pieces. The application sets :max to 5 minus the pieces to add.
{% endcall %} {{ k.sim("condition", "Two requests on one cart line with qty = 2") }}

A refused conditional write still costs write capacity, because DynamoDB read the item to test the condition.

For a rule over several items, DynamoDB has {{ k.term("TransactWriteItems") }}. It groups "up to 100 write actions in a single all-or-nothing operation". The items can be in one or more tables of the same account and Region (DynamoDB transactions). Example: take a seat and write the booking together, and fail both if the seat is taken. A transactional write costs two write units for each item of up to 1 KB.

{{ k.quiz("ddb-q2", "Why does the cart use a ConditionExpression and not a GetItem before the UpdateItem?", ["A GetItem costs more than the UpdateItem", "The test and the write happen in one step", "UpdateItem cannot read the current value", "A condition makes the read strongly consistent"], 1, "Between a GetItem and a later UpdateItem, a second browser tab can add pieces. DynamoDB tests the condition at the moment of the write.") }}

B4Design the key from the questions

In a relational database, you design the tables first and write any query later. In DynamoDB, you list the access patterns first, and then design the key so that each pattern is one GetItem or one Query. This is the main skill of DynamoDB.

Access pattern of the cartThe application knowsOperation
Show my cartmy browser idQuery pk = CART#<browser id>

{{ k.fig("dynamodb-sort-key.png", "three items have the partition key Dog. DynamoDB keeps them in one partition and in the order of the sort key Name: Bowser, Fido, Rover. The Lale Market cart works the same way: one partition key per cart, items sorted by product.") }}

Now a new question arrives: "Which carts contain the book P0044?" The partition key of the table is the cart, so this question has no key. The answer is a {{ k.term("global secondary index") }} (GSI). A GSI is a second copy of selected attributes with a different key. DynamoDB keeps it up to date for you, and each write to the table also writes to the index. The index owns its own key. It borrows the attribute values from the items of the base table.

{{ k.fig("dynamodb-gsi.png", "the index GameTitleIndex has the partition key GameTitle and the sort key TopScore. \"Top scores of Galaxy Invaders\" is now one Query. On the base table, keyed by UserId, the same question needs a Scan.") }} {{ k.sim("gsi", "Which carts contain P0044? Scan of the base table, then Query of a GSI") }}

The Lale Market cart table has no GSI, because the shop never asks this question. Add an index only for a real access pattern: each index adds write cost to every write.

B5Time to live and Streams

An abandoned cart is useless after a day. Each cart item has expires_at, a Unix time in seconds. The table has {{ k.term("TTL") }} on this attribute. DynamoDB "automatically deletes expired items within a few days of their expiration time, without consuming write throughput" (Time to live). Until the delete, an expired item can still appear in a read. A program that must not show it uses a filter on expires_at. This is why the session race in M7 gave DynamoDB only "partly" for exact expiry.

{{ k.term("DynamoDB Streams") }} records each change of an item: insert, update and delete. For each item, the changes keep their order. A consumer, for example an AWS Lambda function, reads the stream and reacts. It sends an e-mail, updates a search index, or writes a copy for analytics. This is how a DynamoDB table becomes the start of an event-driven design. Lale Market does not use Streams. A production shop could use them to empty the cart after an order event, instead of a call from the browser.

Part C

The AWS service: what DynamoDB runs for you

What you must do when you run a key-value store yourself, and what AWS does instead.

C1What you must do when you run a key-value store yourself

Open-source key-value and wide-column databases (for example Apache Cassandra) use the same partition idea. When you run one yourself, you must solve these tasks:

  1. Machines. Select, buy or rent the servers, and install the database on each one.
  2. Copies. Keep each partition on several machines in different data centers, and build a new copy after a failure.
  3. Growth. Add machines when the data grows, and move partitions to them without downtime.
  4. Capacity. Plan for the peak of the year. Machines that wait for the peak cost money all year.
  5. Backups and patches. Back up each node, test a restore, and update the software of every node.

C2What DynamoDB does for you

DynamoDB is serverless. You create a table and send requests. You never see a server. DynamoDB stores each partition in more than one Availability Zone, adds partitions when the data or the traffic grows, and moves the data for you.

The options of M5 (DAX, global tables, Streams, zero-ETL) are all parts of the same service. You turn them on for a table. You do not install them.

C3DynamoDB in Lale Market

  • One table, dbws-cart, in on-demand mode, with point-in-time recovery, TTL on expires_at and encryption at rest.
  • The DynamoDB Engine App runs on an EC2 instance in a private subnet. It reaches DynamoDB through a gateway VPC endpoint, so the traffic does not go to the internet.
  • Authentication uses the IAM role of the instance (SigV4). There is no password. The role allows only the cart table and only the actions that the app uses.
  • The cart page has two experiments: strongly or eventually consistent reads, and a Load Simulation that writes from 200 synthetic shoppers in parallel.
